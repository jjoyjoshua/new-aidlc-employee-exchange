# US-025 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision | Rationale | Alternatives rejected |
| ---- | -------- | --------- | ----------------------- |
| D-01 | **The story's original AC-08 (cancellation email) and AC-09 (push alert) are moved out of `US-025-deactivate-an-account.md` entirely** — not merely deferred inside it — into US-029 and US-032, which already specify the identical behaviour and already cite this story by id. Filed as a Gate 1 change-request (`jjoyjoshua/new-aidlc-employee-exchange#59`). This PR's `acs[]` in the manifest is US-025's full, current AC set; nothing is listed and left unproven | Restating already-owned requirements inside US-025 was duplication, not a second requirement — and `aidlc-check` requires the manifest's `acs[]` to equal the story file's AC set exactly, with every listed AC needing a passing citing test once *any* test exists for the story (`tools/aidlc-check.mjs:298-336`). There is no "listed but intentionally red" state the checker accepts, so "defer inside the story" was not actually available; moving the ACs to where they are already owned was. No notifications module exists yet either way (`apps/api/src/modules/notifications/README.md`: *"Empty until a story fills it"*), the mail vendor is `TBD (owner: IT)` (`app-architecture.md` §5.4 item 4), and building one now would be a new dependency mid-story — `ai/context/task-classification.md`'s hard `STOP-and-ask` override | Leaving AC-08/AC-09 in US-025 and shipping this PR with them untested — rejected, `aidlc-check` fails once any test lands for this story. Building a minimal internal "mailer port" + a `notification_deliveries` log table now, with no live vendor — considered, but that table's shape is itself US-029's design-note scope; building it here pre-empts that story. Pulling in a real vendor now — rejected outright per the override above |
| D-02 | The preview (FR-01) and the cascade's write (FR-02) both read/write the `bookings` table **directly from `users.repository.ts`**, never via a `modules/bookings` import | `eslint.config.mjs`'s `MAY_IMPORT` forbids `modules/users` importing `modules/bookings`. **`app-architecture.md` §2 already grants this exception in writing, before any code existed**: *"`users` owns the deactivation cascade, not `bookings`. BR-001.18 makes cancelling the leaver's desks part of deactivating the account — one act, one transaction, refusable as a whole."* `ADR-004` ("read across, write within") independently legitimises the **read** half — `desks.repository.ts:100-120`'s `countUpcomingConfirmedForDesk` is the standing precedent (corrected per design note §6.1, F12 — the earlier draft of this rationale leaned on "the write happens inside a function," which satisfies the lint rule but not ADR-004's actual SQL-ownership rule; the architecture's own written exception is the real justification) | Composing `AdminBookingsService.listAllBookings` (filtered by a new `userId` query param) for the preview — rejected: that endpoint's shape serves a paginated, multi-person admin table (US-013/US-014), and reshaping the confirmation dialog's very specific "this person's upcoming bookings, desk + date" need around it would make `modules/users`'s screen depend on `modules/bookings`'s response shape, the opposite of ADR-004's boundary. Orchestrating the write from the admin router by calling `usersService`/`adminBookingsService` in sequence — rejected: two separate PostgREST round trips are two separate implicit transactions, which cannot deliver AC-12's "all or nothing" |
| D-03 | The cascade's atomicity is a **single Postgres function** (`.rpc()`), not application-level orchestration with compensation | Both writes (`user_profiles`, `bookings`) are the same Postgres database, which has real transactions. `ADR-011`/`ADR-012`'s compensating-action shape exists for genuinely separate systems (Postgres + Supabase Auth, `createAccount`/`updateAccount`'s own precedent) — reaching for it here, where a transaction is actually available, would be strictly weaker than using one | Two sequential repository calls (`setInactive` then `cancelBookingsForUser`) with a compensating re-activation on partial failure — rejected: strictly more code for a weaker guarantee than a transaction already gives for free |
| D-04 | **No new trigger.** The existing `user_profiles_require_active_admin()` trigger (`0004_last_active_admin_guard.sql`) is reused unmodified for AC-10 | Its own migration comment already states the `WHEN` clause (`old.is_active and old.role = 'admin' and not (new.is_active and new.role = 'admin')`) covers an `is_active` flip identically to a role change — confirmed at US-024 design-note time (§2.4, `ADR-013` Decision item 4). The Architect's own note (§2.4) additionally walks the mechanism step by step (the trigger fires from inside a PL/pgSQL function exactly as from a plain `UPDATE`, and its uncaught exception aborts the whole transaction), rather than re-asserting the conclusion | A second, deactivation-specific trigger — rejected as pure duplication of a rule already enforced |
| D-05 | **`already_inactive` — a target already inactive when the cascade runs (a race, or a stale list) — is reported by the repository as its own outcome, then collapsed by the service into `ok`** (`cancelledCount: 0`, logged) | Mapping it to `not_found` would ship `404 user_not_found` about an account plainly on screen — a lie. Mapping it to the failure state would ship "nothing changed... still active" — also false, and every promise AC-13 makes (cannot sign in, chip reads Deactivated) is already true. Collapsing to `ok` keeps the browser honest with no invented copy and no new error code (design note §2.2) | A distinct `409 account_already_inactive` matching `booking_already_cancelled`'s precedent — rejected for now: it needs a new error code and an SCR-008 state nobody has approved, for a millisecond race (open item 1, routed to the human) |

## Open items for the human (not decided here)

- **D-05's alternative.** Confirmed as D-05 above, or send the `409 account_already_inactive` shape to Gate 1 instead (`design-note.md` open item 1).
- **§4.3's residual (design note).** A booking inserted in the milliseconds around the cascade running is a phantom no lock in this design can see, and can outlive its owner's deactivation — BR-001.18's own harm (a stranded desk). Recovery is a manual admin cancel via US-015. Confirm the residual is accepted and named, rather than fixed (open item 2).
- **Self-deactivation (design note §6.2, F13).** The server permits an admin who is not the last one to deactivate themselves; their very next request is then refused by `require-session.ts`, moments after their own success toast. Should SCR-008 suppress Deactivate on the acting admin's own row, or say something? That is copy nobody has approved (open item 3, routed to UX).
- **NFR-009's 30-day session — narrower than first framed.** `require-session.ts` step 3 already refuses every request from a deactivated account immediately; that is shipped and commented, not open (`spec.md`'s Out-of-scope bullet corrected, design note §4.2). What remains is a Gate 1 formality: confirming `db-design.md` open question 3 against this behaviour (open item 4, routed to BA).
