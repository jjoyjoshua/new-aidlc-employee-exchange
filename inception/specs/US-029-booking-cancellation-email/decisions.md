# US-029 — decisions

| ID   | Decision | Rationale | Alternatives rejected |
| ---- | -------- | --------- | ---------------------- |
| D-01 | `sendBookingCancellation` is composed **inside** `notifications.service.ts`, beside `sendBookingConfirmation`, matching that function's own docblock instruction ("US-029/US-030 should add their own `send*` functions the same way") | This module's charter is the ONE place message wording is decided; the three callers (`bookings`, `admin` router twice) hand over facts, never text — same reasoning as US-028/D-01 | Composing text in each router (repeats US-028's rejected alternative three times over, and puts wording in three modules instead of one) |
| D-02 | The owner-cancel path (US-011) gets its desk number via the ALREADY-injected `availability.getDeskById(desk_id)` (the same method `createBooking` already uses), after widening `cancelOwnedBooking`'s `.select()` from `'id'` to `'id, desk_id, booking_date'` — plain columns, no relational embed | Reuses an existing, already-tested method rather than inventing a second way to resolve a desk number; avoids combining `.update()` with a PostgREST relational embed, a query shape this codebase has never used and has not proven against real Postgres | Embedding `desks(desk_number)` directly onto the `UPDATE … RETURNING` (untested shape in this codebase — `admin-bookings.repository.spec.ts`'s own docblock notes query-pinning tests prove the query issued, not that PostgREST accepts an embed string, and no existing `.update().select('...relation(...)')` call exists anywhere in `apps/api/src` to point at as precedent) |
| D-03 | The admin-cancel path (US-015) and the owner-cancel path resolve the desk number differently: admin-cancel adds ONE follow-up plain read inside `admin-bookings.repository.ts` — `.from('bookings').select('booking_date, desks(desk_number), user_profiles!user_id(email)').eq('id', bookingId).maybeSingle()` — reusing the exact embed shape `listBookings` already proves in the same file, rather than widening `AdminBookingsServiceDeps` with a new cross-module dependency | The admin path also needs the **owner's** email, which `availability.getDeskById` cannot supply and which no method on `UsersService` currently exposes by id; a same-module follow-up read keeps `bookings`/`admin-bookings` self-contained (`coding-standards.md`: "no module imports another module's service") rather than reaching into `users` from a bookings-owned repository or router-composing three separate service calls for one outcome | (a) Router-level orchestration — `admin.router.ts` calling `desks` then `users` then `notifications` separately — works but scatters "what this email needs" across three service calls the router has to stitch by hand, for data one query already answers elsewhere in the same file; (b) widening `AdminBookingsServiceDeps` with a `users` port — crosses the module boundary the standard forbids |
| D-04 | `users.service.ts`'s `DeactivateAccountOutcome` gains `cancelledBookings: CancelledBookingRow[]` on its `ok` branch, additive alongside the existing `cancelledCount` (not replacing it) | The repository already computes and returns this (`users.repository.ts:292-293`, whose own docblock names US-029/US-032 as the intended widener); adding it is a pure widening of an existing type, and keeping `cancelledCount` avoids touching whatever already reads that field | Removing `cancelledCount` in favour of deriving it from `.length` at every call site (a bigger diff for no behavioural gain — nothing asked for its removal) |
| D-05 | Draft transactional copy, one template for all three sources (no AC gives literal wording for the self-cancel or plain admin-cancel body — only AC-04's cascade/admin example is verbatim): `"Your desk {desk} for {date} was cancelled{actorClause}.{rebookInvite}"`, where `actorClause` is `''` for `owner` (AC-05 — passive voice with no actor reads as "no actor named") or `' by your office admin'` for `admin`/`deactivation_cascade` (AC-04's own sentence, verbatim), and `rebookInvite` is `' You can book another desk any time.'` for `owner`/`admin` and `''` for `deactivation_cascade` (AC-06) | AC-05/AC-06 only specify a CONTRAST ("no actor" vs "names the role" vs "role, no rebook invite") — some wording had to be chosen to realise it. One template with two swapped fragments reuses AC-04's own example verbatim rather than drafting three independent sentences, and keeps the three variants provably related instead of three strings that could drift apart under a future edit | A distinct sentence per source (e.g. "You cancelled your desk...") — rejected once the single-template shape turned out to satisfy AC-04's exact wording with no rewrite; leaving the two undictated fragments as an open question and blocking `go` on it — copy this low-stakes is exactly what "offer a sensible default" exists for; the human can edit it in the PR diff before merge with no re-plan needed |
| D-06 | The "Wed 9 Sep" date format (AC-02's own example) is a new pure function, `formatShortDate(date: OfficeDate): string`, added to `apps/api/src/domain/format-display-date.ts`, using `Intl.DateTimeFormat.formatToParts` (weekday-short, day-numeric, month-short) assembled by hand — never `.format()`'s locale string directly | `domain/booking-window.ts`'s own `officeToday` states the reason: `formatToParts`, not a locale format string that happens to look right, because the latter is a bet on locale data staying put. `.format()` with `en-GB` actually emits a comma ("Wed, 9 Sep") that AC-04's example does not have — assembling parts by hand is what avoids that mismatch, not a stricter locale choice | `Intl.DateTimeFormat('en-GB', {...}).format(date)` directly (one line shorter, but its exact punctuation is an implementation detail of the locale table, not something this function should depend on) — also placing it in `notifications/` instead of `domain/` (rejected: it is a pure calendar-date function with no I/O, `domain/`'s own charter, and US-030's reminder email will need the identical format) |
| D-07 | The actor-clause/rebook-invite DECISION (which of the two fragments applies to a given `cancellationSource`) is its own pure function, `cancellationCopy(source): { actorClause, includeRebookInvite }`, in `apps/api/src/domain/cancellation-copy.ts` — `notifications.service.ts` calls it and assembles the final string, but does not itself decide which fragment applies | `domain/README.md` names this exact rule as domain's own charter — "What should this notification say? (BR-001.20)" is listed alongside the booking-window and password rules, and AC-04/05/06 all cite BR-001.20. Found while implementing Step 1 (reading `domain/README.md` as the "verify by reading" step this decision itself demanded), not assumed going into the plan | Composing the whole decision inline inside `notifications.service.ts` (works, matches US-028's `sendBookingConfirmation` precedent, but US-028 had no BR-cited pure rule to extract — this story does, and `domain/README.md` already lists it) |

Cite these as `US-029/D-01` outside this folder.
