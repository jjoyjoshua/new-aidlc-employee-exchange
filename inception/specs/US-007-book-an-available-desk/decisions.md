# US-007 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision | Rationale | Alternatives rejected |
| ---- | -------- | --------- | ---------------------- |
| D-01 | The unique-index violation is identified by matching the known constraint names (`bookings_one_confirmed_per_desk_per_day`, `bookings_one_confirmed_per_user_per_day`) against the Postgres error's `message` (which Postgres formats as `duplicate key value violates unique constraint "<name>"`), not by inspecting the key's column list | The constraint name is the more specific, less ambiguous signal, and it is exactly the string the design decision (`app-architecture.md` §4.1 step 5) refers to when it says "the server maps the violated index to the right answer." A real-Postgres concurrency test (`testing-standards.md`) proves this mapping directly, so a wrong assumption about the error shape fails a test rather than shipping | Parsing the `details` field's key/column list (e.g. `Key (desk_id, booking_date)=(...) already exists`) — workable, but ties the mapping to column order rather than to the named constraint the schema already documents, and is one string-shape assumption instead of a documented Postgres behaviour |
| D-02 | `GET /api/bookings/availability`'s response gains one additive `myBooking` field rather than a second endpoint (e.g. `GET /api/bookings/mine?date=`) | Confirmed with the human at D1 (this plan). AC-06 needs the existing-booking fact **at the same moment** the desk list arrives — a second round trip either delays the check the AC calls "immediate," or forces the client to sequence two requests before it can render anything. The response schema is already non-`.strict()` (US-006's rule), so an additive field breaks nothing already deployed | A second endpoint — correct in isolation, but adds a network round trip on the critical path of the one AC that is explicitly about speed ("before any desk selection, the wasted choice never happens") |
| D-03 | `POST /api/bookings/:id/cancel` (FR-06) is undiscriminating: it returns cancelled, or one `404 booking_not_found` for every other reason (not found, not owned, not currently confirmed) | Confirmed with the human at D1 (this plan, see the D1 chat exchange on AC-07's scope). AC-07 needs only "cancel it, then rebook" from this one entry point; US-011 is the story that owns *why* a cancellation was refused (past-dated, already cancelled, wrong owner) and the richer UI around it. Building that distinction here would be scope this story was not approved for, and US-011 does not list US-007 as a dependency, so it must not assume US-007 already solved its problem | Building US-011's full eligibility/idempotency surface now, "since it's related" — rejected per the human's D1 choice and the DEV charter's "no scope beyond the story" guardrail |
| D-04 | `bookings.repository.ts`'s insert is a single `INSERT ... RETURNING`, with no `SELECT` immediately before it to check availability | This is `app-architecture.md` §4.1 step 4 restated for this repository, not a new decision — "no availability check precedes it." Recorded here so the implementation plan has one place that cites it alongside the constraint-name mapping it depends on (D-01) | A `SELECT` for the desk's current status before the `INSERT`, purely for a friendlier error message on the common case — rejected because it reintroduces exactly the race window the unique indexes exist to close; the friendlier message still has to be produced from the index violation for the case the pre-check missed |
| D-05 | The desk-active check (FR-04) is a plain `SELECT id, is_active from desks where id = :deskId`, not folded into the booking insert via a `CHECK` or trigger | A `CHECK` constraint cannot reference another table in Postgres, and a trigger would move a rule `ai/standards/coding-standards.md` says belongs in `domain/`/`modules/` into the database layer, where this project's own README convention (`apps/api/src/modules/bookings/README.md`) does not put rules. A plain read, same pattern as `listActiveDesks` (US-006), keeps the rule findable in the service | A database trigger enforcing "desk must be active" — technically closes a race with a hypothetical concurrent deactivation, but no such write path exists yet (US-015/US-017 not built) and it would put a business rule where `coding-standards.md` says rules must not live |
| D-06 | AC-07's confirmation dialog is a new, minimal shared component (`apps/ui/src/components/confirm-dialog/`), not a copy pasted into `existing-booking-state`, even though the component inventory (`apps/ui/src/components/*`) has no dialog/modal today | No dialog primitive exists yet in this codebase (verified — `apps/ui/src/components/` has no `dialog`/`modal` directory), and the story explicitly calls this "the cancel confirmation dialog reused from SCR-002 ST-07," i.e. one component two screens share, not two independent implementations. Building it as a shared primitive now means US-011 (which needs the identical dialog for its own cancel flow) extends it instead of reconciling two copies later | A one-off dialog inlined in `existing-booking-state` — faster for this story alone, but guarantees US-011 either duplicates it or has to refactor this story's code to extract it, and "reused from SCR-002 ST-07" in the story text reads as a shared-component instruction, not a coincidence |

| D-07 | US-007's UI (FR-07–FR-16) is built on the **current, merged** `desk-row`/`zone-group` components (US-006, PR #35), not on the uncommitted 2026-09-18 zone-tabs/desk-tile revision found in `inception/design/screens/SCR-003-book-a-desk.md` | Confirmed with the human at D1. That revision is not an approved story — it names itself as needing "a follow-up dev story" (its own Conflict #5) before the product matches it, and building on an uncommitted, unapproved design mid-story would make this story's scope hostage to that spec's own unresolved open questions (its #5 and #6) | Building the tile-grid now "since the spec already shows it" — rejected: it was never approved through Gate 1 for this story, and doing so here would silently absorb a rebuild the spec itself says is a separate delivery decision |

| D-08 | `apps/ui/src/screens/my-bookings/MyBookings.tsx` (still a stub — its booking list is US-010's) gains only a `bookingConfirmation` toast naming the desk, date and email, mirroring the existing `password-saved` toast (US-004/AC-07). AC-03's "visible in Upcoming" is **not** provable by this story and is left unimplemented, because there is no Upcoming list here for a row to be visible in | Discovered during implementation, not anticipated by the plan: FR-10 assumed `MyBookings` already rendered a booking list, but it is explicitly documented as a stub whose content belongs to US-010/US-011. Building a list here would be exactly the scope-creep the DEV charter forbids, and US-010 does not name US-007 as a dependency any more than US-011 did (the same shape of gap as D-03, resolved the same way: build the narrow, testable slice this story can prove, leave the rest to the story that owns it) | Building a minimal booking list in this story so AC-03 is fully provable — rejected, it duplicates work US-010 is explicitly scoped to do and risks disagreeing with that story's own design; leaving FR-10 entirely unimplemented — rejected, the toast half is cheap, directly testable, and is what the story's own screen text (SCR-003 ST-11) actually specifies as this screen's UI contribution |

Cite these as `US-007/D-01` through `US-007/D-08` outside this folder.
