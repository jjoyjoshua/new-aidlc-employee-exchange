# US-027 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision                                                                                                          | Rationale                                                                                                                                                                                                                   | Alternatives rejected                                                                                                                                                    |
| ---- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-01 | The server-side reset-password generator does **not** exclude the ambiguous glyphs (`1/l/I/0/O`) the create-path generator excludes; it satisfies V-12 only. **Recorded as [ADR-014](../../../knowledge/decisions/ADR-014-generated-credential-alphabets.md)** — the Architect design note judged this divergence worth a standing decision record, not just a story-local entry (design note §9) | Human decision, prompted by a real tension the story itself flags as unresolved. The hi-fi Figma frame for ST-11 uses the sample password `q4Lm1I0oTz8v` deliberately, and the design note states outright that the sample "carries `1`, `I`, `0` and `o`, the four glyphs this state exists to disambiguate" — i.e. the design's own intent is that the monospace, disambiguating font at ST-11 carries legibility, not character exclusion. ADR-014 additionally requires every generator to keep excluding characters that break dictation/transport (space, quote, backslash, backtick) regardless of this decision — reusing `generate-password.ts`'s existing special-character set verbatim | Reusing `generate-password.ts`'s full exclusion set for consistency across both generators — rejected because it would contradict the approved hi-fi design's own reasoning for why the credential field exists in the shape it does |
| D-02 | `Dialog` gains a new `dismissible?: boolean` prop, default `true`; when `false` the close icon is not rendered and Escape is suppressed regardless of `busy` | AC-04 requires the shown-once result dialog to have no dismissal path at all — not merely a disabled one. `Dialog.tsx` today only ever *disables* the close icon via `busy` (`dialog.tsx:122`); it is still rendered and visually present. The design note is explicit that ST-11 draws **no ✕ in its header** at all — a `busy`-only workaround leaves a visible, if inert, icon that is honest about state but not about intent | Passing `busy={true}` permanently for the result phase — rejected: the icon still renders (`disabled`, not absent), which does not match the approved design's explicit "no ✕ in its header" note and reads as a stuck loading state rather than a completed, closed-off result |
| D-03 | The reset endpoint calls no `requireActingAdmin` / writes no attribution column                                    | The story's ACs do not ask for attribution of who performed the reset, and no such column exists on `user_profiles`. `changeRole`'s route is the existing precedent for an admin write with no attribution (as opposed to `deactivate`'s `cancelled_by`) | Adding an attribution column — out of scope; not asked for by any AC, and a schema change would re-tier a decision that is otherwise already Complex for other reasons |
| D-04 | The server-side generator lives at `apps/api/src/domain/generate-reset-password.ts`, a new pure function, not a shared refactor of `apps/ui/src/lib/generate-password.ts`. **See [ADR-014](../../../knowledge/decisions/ADR-014-generated-credential-alphabets.md)**, which records the general rule this decision is one instance of: a generated credential's alphabet follows how it is delivered, not one project-wide rule | The story's own API-impacts section requires server-side generation (unlike account creation, which accepts a client-supplied password); the two generators serve different acts (creation vs. reset) and, per D-01/ADR-014, now also differ in their exclusion rules, so unifying them would either force the create-path to inherit D-01's exclusion change or require a parameterised generator neither story asked for. A shared generator would also have to live in `libs/contracts`, putting credential minting in browser-bundled code | A shared generator function parameterised by an "exclude ambiguous glyphs" flag — rejected as speculative generality for two call sites that already differ in where they run (browser vs. server) and, after D-01, in policy |
| D-06 | The reset write order is `armMustChangePassword` (the `user_profiles` write) **first**, then `usersAuth.setPassword` (the Supabase Auth write) **second** — with no preceding `findById`; the profile write is itself the existence check | Architect design note blocker finding (F1): the originally planned order (Auth first) could leave an account holding a password nobody has ever seen if the profile write then failed, defeating AC-09 and locking the person out while ST-13 says "Nothing has changed." `updateAccount` (`users.service.ts:231-304`) already established this exact order for the sibling cross-system write, per ADR-012 | Auth-first, matching the plan's original draft — rejected once the Architect review traced the failure mode against AC-09 and ADR-012's own precedent; the residual of the corrected order (an armed flag with an unchanged password on Auth failure) is strictly smaller, see design note §2.4 |
| D-05 | The reset response uses a new schema, `resetPasswordResponseSchema`, rather than adding a `password` field to `adminUserSchema` | `adminUserSchema` is the shape returned by `GET /users`, `POST /users`, and every other admin-list-adjacent response; adding a one-time credential field to it would make that field a de facto part of the account's public shape rather than a fact true only of this one response | Extending `adminUserSchema` with an optional `password` field — rejected: every other consumer of that schema would need to remember the field is never actually populated outside this one route, which is exactly the kind of ambiguity `emailTakenDetailsSchema`'s own precedent (a purpose-built schema per distinct response shape) exists to avoid |
