# US-002 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision                                                                                                     | Rationale                                                                                                                                                                                                                                                                                             | Alternatives rejected                                                                                                                                                                                   |
| ---- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-01 | Sign-out mounts **outside** `requireSession` entirely — no session middleware runs on this route              | Adopted from the Architect's design note §2.2: every step of the chain either already refuses nothing worth refusing for this request, or (step 3, `is_active = false`) actively prevents the one revoke that matters. AC-04 then holds structurally — US-004 adds a gate to a chain this route never runs, rather than a string comparison a future author must remember | Mount behind `requireSession` and allowlist the route in step 5 — makes a security criterion depend on a path comparison written by a different story, and risks confusing `req.path` with `req.originalUrl` under the `/api/auth` mount |
| D-02 | Sign-out answers **`204` for every input** — a missing, malformed, expired, or already-revoked token all included | Adopted from the design note §2.1: AC-02 asks that a session no longer authorise anything, not that sign-out reject a session that already does not. There is no ST-## anywhere for a failed sign-out, and the story explicitly rules out a confirmation state. **Defensible either way — flagging for override**: the alternative below is not wrong, only a different trade-off | `401` when no `Authorization` header is present, `204` otherwise — makes a client bug (no token sent) loud immediately, at the cost of reintroducing a failure state the product never asked for. The browser ignores the response either way (D-03), so a server-side warning log is the chosen signal instead |
| D-03 | `revokeSession(accessToken, scope)` — `scope` becomes an **explicit, required** argument, not a default          | The existing hardcoded `'global'` is correct for US-001's deactivated-account refusal and wrong for sign-out (the story's own words: *"the next person to use **this browser** cannot act as me"*, not every device). A required argument makes both call sites state their intent where a reviewer can see it, and a compile error catches an omission rather than a silent wrong scope | A second method `endSession` alongside `revokeSession` — hides the same decision behind a name instead of a visible argument. A default value on `scope` — puts the more destructive (`global`) behaviour one forgotten argument away |
| D-04 | The browser proceeds to `/sign-in` regardless of what `POST /sign-out` answers, and regardless of whether it even completed | A transport failure must not strand a user on a signed-in screen mid-departure; there is no UI state for a failed sign-out and SCR-010 (US-004) is explicit that an outage must never trap someone. Local state (`user`) is cleared unconditionally | Blocking navigation until the server confirms — leaves a user stuck on a signed-in screen exactly when they are trying hardest to leave it |
| D-05 | `AccountMenu` is built as a **disclosure** (`<button aria-expanded aria-controls>` revealing ordinary buttons), not `role="menu"` | A real ARIA menu obliges arrow-key roving, `aria-activedescendant`, typeahead and wrap-around; a partially built one announces affordances it does not have, which is worse for a screen-reader user than a plain disclosure. AC-01 asks for "present and operable by keyboard," which a disclosure meets exactly with one row in it | A full `role="menu"` implementation — correct eventually, but this story ships one item (Sign out) and the second row (Settings) is a future story's to add; building the fuller pattern now is speculative for a menu with one entry |

## Open for the human's confirmation, not blocking D1

| # | Item | Why it is not blocking |
| - | ---- | ----------------------- |
| 1 | Scope `local` (this device only) vs `global` (every device) for a user-initiated sign-out | The story's own sentence ("this browser") already answers it; flagged in case the product intends "sign out everywhere" as a distinct future action rather than the default |
| 2 | D-02's `204`-always vs `401`-on-missing-token | Both are defensible; `204` is adopted as the default and is reversible without touching any other decision in this package |
