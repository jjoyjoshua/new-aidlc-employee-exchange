# US-030 — decisions

| ID   | Decision | Rationale | Alternatives rejected |
| ---- | -------- | --------- | ---------------------- |
| D-00 | This story is implemented against the EXISTING design in `app-architecture.md` §4.3 and US-034's `design-note.md` §2.3, rather than requesting a fresh Architect design note. Confirmed with the human before writing this plan | Both documents were written anticipating this exact story: §4.3 specifies the route/mechanism/idempotency in full; §2.3 specifies the `recordAndSend` extension and the `23505`-is-expected instruction, by name, for this story. Nothing about implementing it surfaced a gap in either | Routing to `/architect` for a new note first — rejected because it would re-derive answers already on file, and the human confirmed proceeding directly |
| D-01 | `recordAndSend` gains an internal branch keyed on `input.kind === 'reminder'`, calling a new private `recordAndSendClaimFirst` helper; it is NOT split into two exported functions, and `sendReminderEmail` calls `recordAndSend` exactly like the other two composers | `design-note.md` §2.3's own instruction: "US-030 extends this function; it does not write a second one (AC-08)" — read literally as `recordAndSend` itself, not merely "the notifications module." Keeping one exported entry point means a future caller cannot pick the wrong path by choosing the wrong function name | A second exported function (`recordAndSendReminder`) beside `recordAndSend` — technically still "one module, one mailer boundary," but a caller could still call the wrong one; the design note's wording reads as ruling this out specifically |
| D-02 | Idempotency is a REPOSITORY-level claim, not a service-level check: `claimReminderSent` attempts the INSERT first and treats its `23505` (scoped to the exact index name, matching `insertConfirmedBooking`'s own precedent of checking the message rather than trusting any `23505`) as `{ claimed: false }` — never a SELECT-then-INSERT | "Write first, then explain" is this codebase's standing discipline for every other race in the system (`cancelOwnedBooking`, `insertConfirmedBooking`) — a read-then-write here would reopen exactly the TOCTOU window those functions exist to avoid, this time between two runs of the SAME scheduled job | A `SELECT` for an existing sent row before inserting — rejected for the same reason every other repository method in this codebase rejects it: the gap between the read and the write is exactly where two overlapping runs would double-send |
| D-03 | The claim insert and the failure demotion are two new repository methods (`claimReminderSent`, `markDeliveryFailed`), added beside the existing `insertDelivery` — which stays untouched and keeps serving `sendBookingConfirmation`/`sendBookingCancellation`'s send-then-record path | Widening `insertDelivery` itself (e.g., a mode flag) would touch the one method both existing, already-merged composers depend on, for no benefit to them — a new method pair is strictly additive and the impact-analysis's "zero behavioural change" claim for US-028/US-029 is then true by construction, not by careful testing alone | Reworking `insertDelivery` into `claimReminderSent`'s shape and having confirmation/cancellation pass a "no claim needed" flag — more surface change for the same outcome |
| D-04 | A new `modules/reminders` owns the repository/service/router for this story, rather than extending `modules/bookings` or `modules/notifications` | Matches this codebase's established one-module-per-capability pattern (`auth`, `bookings`, `desks`, `users`, `admin`, `notifications`) and its own stated rule that no module imports another module's service; `notifications` already has a named asymmetry (calls nobody) that a booking-listing responsibility would break, and `bookings`'s module owns request-triggered booking writes, not a scheduled read across all bookings | Adding `listConfirmedBookingsForDate` to `AvailabilityRepository` and the run/route to `modules/bookings` — rejected because `bookings.router.ts` is mounted behind `requireSession` at `/api/bookings` (`http/app.ts:84`), the wrong guard entirely for an unauthenticated-by-session internal route |
| D-05 | The shared secret travels in a custom header, `X-Reminder-Run-Secret`, compared with `crypto.timingSafeEqual` after a length check (unequal lengths fail fast, never call `timingSafeEqual` on mismatched buffers, which throws) | `Authorization: Bearer <token>` would visually resemble the session token scheme `requireSession` already owns, inviting a future reader to assume this route accepts a session — `app-architecture.md` §4.3 is explicit that it does not. `timingSafeEqual` is the standard defence against a timing side-channel on a secret comparison; this codebase does not compare secrets anywhere else, so there is no existing precedent to match instead | `Authorization: Bearer` (rejected for the naming confusion above); a plain `===` string comparison (rejected — leaks timing information about how many leading bytes matched, the standard reason `timingSafeEqual` exists) |
| D-06 | `POST /api/internal/reminders/run` returns a small JSON summary — `{ kind: 'skipped', reason: 'weekend' } \| { kind: 'ran', date, attempted, sent, failed }` — rather than an empty `200` | No UI consumes this route; a monitoring/ops caller (whatever triggers it) benefits from a body it can log or alert on, and the shape costs nothing since the service already computes these counts to satisfy AC-10 | An empty `200.end()`, matching the cancel routes — rejected because those routes have a browser on the other end reading nothing by design (US-011/US-015's own precedent); this route's only consumer is infrastructure, and an empty body would make a failed run indistinguishable from a skipped weekend in the one place — logs — anyone would look |
| D-07 | AC-08 ("a booking made after the run still gets no second run") needs no dedicated guard code — it is proven by the ABSENCE of any catch-up mechanism: the service holds no record of past invocations, computes only "tomorrow" relative to whenever it is called, and nothing calls it more than once per day in production (out of scope, D-00/spec.md) | Building a "have I already run today" guard would be speculative generality this story's own AC-08 explicitly disclaims ("not a catch-up... if the PO wants a catch-up, it is a rule change") — the correct amount of code for "no catch-up" is no catch-up code | A `reminder_runs` table tracking the last invocation's date, refusing a second same-day run — solves a problem nobody asked for and the story explicitly rejects |

Cite these as `US-030/D-01` outside this folder.
