# US-005 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision                                                                                                          | Rationale                                                                                                                                                                                                                     | Alternatives rejected                                                                                                                                                                        |
| ---- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D-01 | `office.today`/`office.timezone` ride the existing sign-in and session responses rather than a new `GET /api/office` | Confirmed with the human before this plan (Architect design note §1.3–1.4, open item 1). No second boot round trip for two scalars; `today` is time-varying and not cacheable anyway, so the usual config/session split buys nothing here | A dedicated `GET /api/office` endpoint. Cleaner-looking in isolation, but adds a route mount to a module (`bookings`) that stays otherwise empty in this story, for no functional gain today |
| D-02 | `libs/contracts/src/index.ts`'s docblock and `eslint.config.mjs` Boundary 5's message are corrected to say the wire contract also carries requirement-level rules both sides must evaluate identically | Both already say "the rules live in `apps/api/src/domain`", which `password.ts`'s `evaluatePasswordPolicy` already contradicts (Architect design note §2.1, open item 2). A second silent contradiction is worse than fixing the sentence | Moving the shared date-window predicates into `apps/ui` and accepting a duplicated weekday rule. Rejected — two implementations of BR-001.3 is exactly the drift ADR-002 exists to prevent |
| D-03 | One shared date-formatting helper in `apps/ui`, used by the date strip, the calendar and its footer                | `new Date('YYYY-MM-DD').toLocaleDateString()` renders the wrong calendar day for a viewer west of Greenwich (design note §2.8) — the single most likely defect in this story. One helper fixes it once rather than at three call sites independently | Formatting inline at each call site. Rejected — the trap is easy to reintroduce piecemeal, and AC-07's cross-timezone test should fail loudly, once, if it regresses |
| D-04 | The latest-wins seam (`use-availability.ts`) lives private to `apps/ui/src/screens/book-a-desk/`, not in `lib/api-client.ts` | Latest-wins is a property of this screen's interaction (AC-08), not of the transport — the transport's behaviour was already fixed by US-001 design note §9.4 | Building request cancellation into `api-client.ts` generically. Rejected as scope beyond this story; no other screen has asked for it yet |
| D-05 | `refusalFor`'s precedence is fixed: `past` → `too-far-ahead` → `closed`                                             | A past Saturday must read **Past**, not **Closed** — checking the weekend rule first would give a technically-true but worse answer for a date whose real problem is that it has gone (design note §2.4) | Checking `closed` first, or returning all matching reasons. Rejected — AC-04 asks for one readable reason per date, and an unordered check makes the "past weekend" case non-deterministic |
| D-06 | AC-07's page header (title + office timezone) is rendered by the `BookADesk` screen itself, not by modifying `AppShell` | `AppShell.tsx`'s own docblock declares it a structural stub whose hi-fi treatment belongs to later stories (US-010/US-013), matching the human's direction to track the shell/sidebar mismatch as its own change, not this PR's. Every existing screen already renders its own heading this way (`MyBookings` renders its own `<h1>`; `AppShell` supplies nav only) | Modifying `AppShell` to add a page-header slot, as the design note's §0 surface analysis first suggested. Rejected during implementation — it would touch the shared shell the human asked to leave alone, for a requirement (AC-07) that is scoped to one screen's header, not to every screen's |

Cite these as `US-005/D-01` through `US-005/D-06` outside this folder.
