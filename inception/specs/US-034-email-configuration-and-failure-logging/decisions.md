# US-034 — decisions

| ID   | Decision                                                                                                                         | Rationale                                                                                                                                                                                                     | Alternatives rejected                                                                                                                                                    |
| ---- | --------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-01 | Implement exactly one transport, `console` — writes a structured log line via `infra/logger` and reports success. No mail SDK dependency added. | The production provider is `TBD (owner: IT)` (story's own Edge cases); picking one now would invent a fact the story explicitly says is not this story's to invent, and `security-standards.md` requires Architect + human approval for any new dependency this story has no grounds to ask for | A fake HTTP transport (adds complexity, still guesses shape of a real SDK); choosing a real provider now (not this story's decision, no approval sought)               |
| D-02 | `sendMail` and `recordAndSend` report outcome as a discriminated result (`{ok:true}` / `{ok:false; error}`), never an exception   | AC-07 requires a mail failure never to put the caller's own action at risk; a result type makes "never throws" a type-level property of the function, not a convention a future edit can quietly break        | Try/catch left to every caller (repeats the same guard three times, in US-028/029/030, instead of once here)                                                            |
| D-03 | `infra/mailer` is importable only from `modules/notifications`, enforced by a new `eslint.config.mjs` rule mirroring the existing `infra/supabase` boundary | AC-08 says all three message types go through the *same* path; a lint rule makes a second, ad-hoc mail path a build failure rather than a review comment that can be missed                                  | Trusting code review alone (already the standing risk `infra/supabase`'s own rule exists to avoid)                                                                     |
| D-04 | `notification_deliveries` is created **whole** in this story's migration — every column, all three enums, the reminder partial-unique index — though nothing exercises the reminder path until US-030 | Matches the project's own precedent (`0003_bookings.sql`'s design note §1.1: a table created without its constraints is a different table); `db-design.md` §1.5 already specifies the full shape             | Splitting the index into a later migration when US-030 lands (would retrofit REQ-025's idempotency answer onto rows never constrained by it, repeating the exact mistake `0003_bookings.sql`'s note warns against) |
| D-05 | `MAIL_PROVIDER` is `z.enum(['console'])` at boot, plus a `superRefine` refusing `console` under `NODE_ENV=production`, rather than an unrecognised-value throw inside `sendMail` at first send | Architect design note §1.2 (F-3): AC-04 is a boot-time guarantee per `app-architecture.md` §5.4; a first-send throw is caught by `recordAndSend`'s never-throws contract and never surfaces, and `console` in production would report `sent` while sending nothing | The originally planned first-send throw (unobservable in production once `recordAndSend` exists); leaving `MAIL_PROVIDER` as a free string (lets an unimplemented provider boot green) |
| D-06 | `SendMailResult`'s failure `error` is a **closed string-literal union** (`MailFailureReason`: `'transport_rejected' \| 'transport_unreachable' \| 'transport_unknown'`), never a free-text string — a transport maps its cause to one of these before it leaves `infra/mailer`, so there is no path by which a raw error, a response body, or a credential can reach the log or `error_detail` | Architect design note §4 (F-5), sharpened: a *sanitizing function* over free text is still a heuristic that can miss a shape it wasn't written for; a closed type makes "no credential in the failure reason" true by construction, not by a filter that has to be kept in sync with every future transport | A sanitizing/redacting function over a free-text `error: string` (the design note's literal suggestion — works, but is a heuristic filter rather than a structural guarantee, and needs its own test per failure shape) |
| D-07 | `recordAndSend`'s delivery-log write is wrapped in its own `try`; a failure there is logged in full and reflected as `recorded: false`, never silently dropped alongside a "never throws" catch | Architect design note §2.2 (F-4): a blanket catch around both the send and the record would lose the one case AC-05 most needs — mail and database failing together, which are correlated, not independent | A single try/catch around the whole function (loses the delivery-log failure itself, the exact gap NFR-005 exists to close) |

Cite these as `US-034/D-01` outside this folder.
