# US-031 — decisions

> Technical choices made while implementing this story. Choices that change the shape of the
> system already went to the Architect — see [`design-note.md`](design-note.md) and
> [ADR-015](../../../knowledge/decisions/ADR-015-web-push-library.md). What follows are the
> ordinary implementation-level calls the design note leaves to DEV.

| ID   | Decision | Rationale | Alternatives rejected |
| ---- | -------- | --------- | ---------------------- |
| D-01 | Feature files live at `apps/ui/src/screens/settings/` (`Settings.tsx`, `use-push-settings.ts`, `copy.ts`, `settings.css`, …), not `features/account/` | SCR-004's own "Surface" line says `features/account`, but no `features/` directory exists anywhere in `apps/ui` — every screen (`my-bookings`, `book-a-desk`, `set-password`, `people`, …) lives under `screens/<name>/`. Following the codebase's actual convention over the spec's aspirational path keeps this screen consistent with the other nine | A new `features/` directory for this one screen — inconsistent with every other screen, and a precedent nobody asked to set |
| D-02 | Three new shared components — `Toggle`, `NoteRow`, `DefinitionList` — live at `apps/ui/src/components/toggle/`, `.../note-row/`, `.../definition-list/`, mirroring `components/alert/`, `components/skeleton-row/` | Existing convention: one folder per shared component, `Component.tsx` + `component.css` + `Component.spec.tsx` | Nesting them under `screens/settings/` as screen-private — SCR-004's own component table calls them library additions, and `db-design`-adjacent conventions treat anything reusable as `components/` |
| D-03 | The subscribe/unsubscribe browser mechanics (service worker registration, `Notification.requestPermission`, `pushManager.subscribe`) live in a pure-ish helper module `apps/ui/src/lib/push-subscription.ts`, separate from the fetch wrappers in `lib/push-settings.ts` | Mirrors the existing split between `lib/cancel-booking.ts` (fetch) and screen-local orchestration hooks — keeps the one function that touches `navigator`/`Notification` unit-testable behind a thin seam, same shape as `lib/auth`'s adapter pattern | One monolithic hook doing both the browser calls and the fetches — harder to unit-test the state machine in §6 of the design note without mocking the whole browser API surface inline |
| D-04 | `use-push-settings.ts` follows `use-my-bookings.ts`'s load/loading/error convention (a `status` union: `'loading' \| 'ready' \| 'error'`, plus the ST-05/06 derived flags computed from `Notification.permission` and feature detection) | Established pattern in this codebase for screen data; keeps `Settings.tsx` a thin renderer switching on a status enum, as `MyBookings.tsx` does | A single boolean `loading` + `error` pair — insufficient to represent all eight states without the component re-deriving logic the hook should own |
| D-05 | ST-07's opt-out failure copy is *"We couldn't save that change. Your alerts are still on."* — the direct mirror of the approved opt-in failure sentence, flagged in the PR description as provisional pending UX sign-off | Human deferred this call to DEV (chat, 2026-09-21) rather than blocking on UX. AC-07 requires "the current reality rather than the intent," and the mirrored sentence is the minimal, obviously-correct extension of an already-approved pattern | Leaving the state without copy until UX responds — blocks the PR on a one-line string with an obvious answer; inventing unrelated wording — risks a UX rewrite whereas the mirror is unlikely to need one |
| D-06 | The service worker registers from `use-push-subscription.ts`'s opt-in flow only, calling `navigator.serviceWorker.register('/sw.js')` — no change to `main.tsx` | Design note §8.2 — registering at boot installs a worker for every visitor, most of whom never opt in, and implies offline capability the app does not have | Registering in `main.tsx` unconditionally — rejected by the design note directly |

Cite these as `US-031/D-01` outside this folder.
