# US-010 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision                                                                                                   | Rationale                                                                                                                                                                                            | Alternatives rejected                                                                                                                                   |
| ---- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D-01 | Adopt the design note's API shape (§1), derivation placement (§2, §3) and `StatusChip` extension (§4.4) verbatim, with no DEV-level deviation | The note already resolved the trade-offs against this codebase's real files, with file:line citations; re-litigating in the plan would just restate it with more risk of drifting from what was reviewed | Redesigning any part of §1/§2/§4.4 independently — rejected, no new information surfaced during planning that the note didn't already have |
| D-02 | Split the UI into `MyBookings.tsx` (orchestration + sections), `BookingRow.tsx` (one row), `use-my-bookings.ts` (fetch/accumulate state), `fetch-my-bookings.ts` (the `ApiResult` adapter), and `copy.ts` (state text) | Mirrors `book-a-desk`'s existing split exactly (design-note §4.3) — the only precedent in this codebase, and it already separates concerns the way AC-06/AC-07's "assert the two messages differ" test needs (`copy.spec.ts` testing strings with no rendering) | One large `MyBookings.tsx` — rejected, makes `copy.spec.ts`'s AC-06-vs-AC-07 wording test impossible without mounting the component |
| D-03 | `icon-close.svg` is downloaded from Figma (`Icon / close`, node `11:50`, "Dismiss a dialog") and added as `apps/ui/src/assets/icon-close.svg`, matching `icon-clock.svg`'s existing treatment — **superseding this row's earlier plan to hand-draw one** | Once the Figma file was actually opened (Joy Joshua's corrected links), the asset turned out to already exist in the design system; using the real one is strictly better than approximating it, and costs nothing extra | Hand-drawing a close/X icon to match the existing stroke weight/viewBox — was the fallback plan while the Figma file appeared inaccessible; no longer needed |
| D-04 | Test file layout follows the existing `bookings.*.spec.ts` sibling-file convention exactly (`bookings.repository.spec.ts`, `bookings.service.spec.ts`, `bookings.routes.spec.ts`) rather than a nested `__tests__/` folder | Matches every existing module in `apps/api/src/modules/bookings/` — no new convention introduced for one story | A `__tests__/` subfolder — rejected, inconsistent with the rest of the module |
| D-05 | `BookingRow` renders **no `Cancel` control** in this story, even though the approved `Booking row`/`Today booking` Figma components (nodes `83:5041`, `85:5030`) show one on every Upcoming/Today row | Cancellation's behaviour (opening the confirm dialog, wiring the click) is explicitly US-011's, per `spec.md`'s Out of scope. Rendering a `Cancel` button with no handler would be a dead control — the system's own guidance is not to leave half-finished pieces behind | Rendering `Cancel` as a disabled/inert button now, matching the frame exactly and wiring it in US-011 — rejected: a visibly-present-but-nonfunctional button is worse than a screen that visibly hasn't reached that feature yet, and this codebase's precedent (US-006 → US-007 building up one screen across stories) already accepts screens looking incomplete between stories |
| D-06 | A `loadOlder()` request that fails leaves the accumulated list untouched and clears `loadingOlder` — no error surfaced beyond the "Show more" control simply being pressable again | No AC covers a failed OLDER page (AC-09 is about the *initial* load); blanking the whole list over a "Show more" failure would lose data already on screen, which is worse than a silent retry the control itself invites | A dedicated inline error under the Past section for a failed older-page load — deferred as unrequested scope; nothing in SCR-002's ten states describes it |
| D-07 | "Past bookings" is a native `<details>`/`<summary>` disclosure, open by default | Genuinely functional (keyboard- and screen-reader-accessible collapse) with no new component and no JS toggle state, matching the confirmed "expanded on desktop" frame (node `102:5940` et al.). True responsive default-collapsed-below-768px is not tested by any AC in this story | A stateful `Accordion`/`AccordionHeader` component reproducing the Figma component 1:1, including the chevron-direction and collapsed-on-mobile behaviour — deferred: no AC tests it, and forcing a native `<details>`'s `open` state per breakpoint without JS is not reliable, so building the fuller component now would either be non-functional at some width or need JS anyway |

Cite these as `US-010/D-01` outside this folder.
