# US-015 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID | Decision | Rationale | Alternatives rejected |
| --- | --- | --- | --- |
| D-01 | `POST /api/admin/bookings/:id/cancel`, reusing `cancelBookingParamsSchema` verbatim, `200` with an empty body, no new response schema | Mirrors `POST /api/bookings/:id/cancel` exactly — the only visible difference between the two cancel endpoints is which mount they sit on, which is the whole of the authorization difference. `libs/contracts` needs no change: the outcome set (`ok`/`already_cancelled`/`not_found`) is already fully expressed by HTTP status + existing error codes (design-note §2) | A response body echoing the outcome — rejected, it would add a second source for a fact the status line already carries. `DELETE` — rejected, the row survives the transition (AC-04), so this is a state change, not a deletion |
| D-02 | The write (`cancelAnyBooking`) and its disambiguating read (`findBookingState`) both go on `AdminBookingsRepository`/`AdminBookingsService`, not on `AvailabilityRepository` or inside `modules/admin` | US-013/D-08 put the admin read in `modules/bookings` specifically because "US-015 will WRITE `bookings`" — this is that write, landing where it was already predicted to land. Putting the disambiguating read on `AvailabilityRepository` (which is scoped-by-construction everywhere else) would be a copy-paste hazard on the exact invariant US-006/AC-06 and US-007/D-03 depend on (design-note §3.1) | A new object under `modules/admin` — rejected, ADR-004's one hard rule is that only the owning module writes a table, and `bookings` is owned by `modules/bookings`. A sibling method on `AvailabilityRepository` — rejected, it is scoped-by-construction and a version without `.eq('user_id', …)` sitting three lines from `findMyBookingState` is the copy-paste hazard `AdminBookingsRepository` exists to prevent |
| D-03 | No new ADR. The write reuses US-011's write-first-then-classify primitive, the existing `status='confirmed'` predicate as the sole concurrency guard (no row-version column, because the `confirmed → cancelled` transition is one-way and terminal), and ADR-004's/US-013's already-written placement rule. Three forward constraints for US-029/US-032 are recorded here instead of in a new ADR: (1) the email must go to `bookings.user_id`'s address, never `cancelled_by`'s; (2) wording must key off `cancellation_source`, never off comparing `cancelled_by` to `user_id`; (3) any send must be triggered by the cancel write's own returned row, never by the router's `200` and never on the `409` branch | None of the candidate decisions bind work beyond this story with a genuinely rejected alternative a future author would re-litigate — each either applies an existing rule by name or is a proof that belongs in a repository docblock, not a document with a rejected-alternatives table (design-note §7) | An ADR for "the status column is the optimistic-concurrency guard" — considered, and would be defensible if other terminal-state transitions were expected soon (a desk retirement, an account deactivation); not built because the proof is specific to this table's state machine today |
| D-04 | `AdminSkeletonRow`'s 360px card skeleton moves from 160px (US-013/D-04's height, chosen when no row was ever cancellable) to 188px | Adopting the Architect's recommendation. A mixed list now has both 188px cancellable cards and 160px non-cancellable ones; the skeleton can only match one shape, and 188px matches the common case — PRIN-1's "arrives showing today," and today's rows are the cancellable ones (design-note §5.5, open item 3) | Keeping 160px — rejected, it would mismatch the majority of real rows. A middle value — rejected as solving neither case correctly. **This is a cosmetic default per Auto-mode guidance**, not yet confirmed with UX; cheap to revise (~one CSS value) if UX rules otherwise |
| D-05 | Dialog and toast copy uses the employee's full name (`item.employeeName`) everywhere, including the possessive (`${fullName}'s desk?`), with no special-casing for a name ending in *s* | Adopting the Architect's recommendation. Deriving a "first name" from `full_name` would mean assuming the first whitespace-delimited token is the given name, which this product has no rule for and which is false for a meaningful fraction of real names. The Figma frames' "Priya" reads naturally only because the example's short form happens to match the first token (design-note §5.5, open item 4) | Deriving and using a first name — rejected as an unfounded assumption about name structure. **This is a copy default per Auto-mode guidance**, not yet confirmed with UX; cheap to revise if UX rules otherwise |
| D-06 | Build the focus-return fix for ST-11: a `justCancelledId` held by `AllBookings`, `tabIndex={-1}` on the row, and an effect that focuses the row after the dialog unmounts (whose own focus-restore fires first, then the row) | Adopting the Architect's recommendation. `ConfirmDialog` restores focus to whatever triggered it, but that element (the row's own Cancel button) is gone from the DOM after a successful cancel, so an unfixed flow drops a keyboard user's focus to `<body>` — the opposite of ST-11's explicit "Focus returns to the row, which still exists" (design-note §5.6, open item 7) | Accepting focus falling to `<body>` — rejected, ST-11 states the behaviour explicitly even though no AC numbers it, and the fix needs no change to any shared component |
| D-07 | A past-dated cancel attempt returns the generic `404 booking_not_found`, identical to "no such booking" — no new error code, no third dialog message | **Confirmed with the human (2026-09-19).** Matches the employee cancel endpoint's existing behaviour and the two-message set SCR-005 ST-10 already has approved copy for. The anti-enumeration reason that forced this same fold on the employee endpoint (US-011) doesn't strictly apply here (an admin can already read every booking's status via `GET /api/admin/bookings`), but the screen spec and the no-speculative-generality rule both argue against building a third message with no approved copy (design-note §2.4) | A distinct error code + a third dialog message for "no longer cancellable" — considered and rejected by the human; accepted cost: a tab left open across office midnight can show a "try again" message that can never succeed, across every one of today's rows, until the page is reloaded |
| D-08 | The "already cancelled" dialog keeps its approved copy, "{employeeName} has already cancelled this booking," even though the endpoint cannot actually distinguish the employee cancelling first from a second admin's tab winning the race | **Confirmed with the human (2026-09-19).** The inaccurate-actor case only arises when two admins race to cancel the same booking, which is rare, and the sentence remains true about the booking's state even when the named actor is wrong (design-note §3.3, open item 2) | Rewording to an actor-neutral sentence ("This booking has already been cancelled.") — considered and rejected by the human in favour of keeping the approved Figma copy exact |
| D-09 | Land the disclosure-rule standards edit (`ai/standards/api-standards.md` §Errors) in this PR, rather than carrying it forward again | **Confirmed with the human (2026-09-19).** US-011 open item 4 already routed this edit to the standards file and it was never actioned; US-015 is the first story to sit on the permissive side of the same rule, making this the natural moment to land it (design-note §7) | Leaving it as a follow-up a third time — considered and rejected by the human |

Cite these as `US-015/D-01` through `US-015/D-09` outside this folder.

Three of these (D-04, D-05, D-06) are DEV defaults adopted from the Architect's recommendations, per Auto-mode guidance to proceed on a reasonable, cheaply-reversible default rather than stall Gate D1 on cosmetic/copy decisions that don't change the plan's shape. They are non-blocking for Gate D1 and are called out again in `implementation-plan.md`'s Open questions section for visibility.
