# US-028 — decisions

| ID   | Decision                                                                                                   | Rationale                                                                                                                                                                                                     | Alternatives rejected                                                                                                                                            |
| ---- | ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D-01 | The confirmation's subject/body is composed **inside** `notifications.service.ts` (a new `sendBookingConfirmation`), which then calls US-034's `recordAndSend` — `bookings` hands over raw facts (email, desk number, date), never the composed text | `modules/README.md`'s own charter: "no other module asks ... what the message should say. Callers hand over a booking and an event; this module decides." `recordAndSend`'s signature (US-034) takes pre-composed `subject`/`body` because US-034 had no caller yet to decide FOR; US-028 is that caller, and this is where the decision actually gets made | Composing the text in `bookings.router.ts` and calling `recordAndSend` directly (works, but puts message wording in the wrong module and contradicts the stated charter) |
| D-02 | The send is wired into `bookings.router.ts`'s `POST /` handler, called and awaited after `outcome.kind === 'ok'`, using `req.user.email` (already loaded by `requireSession`, no second read) — not inside `bookings.service.ts`'s `createBooking` | `createBooking` has no `userEmail` parameter today and adding one would touch a function every existing US-007/009/011 test already exercises; the router already holds the email for the identical purpose (the existing `confirmationEmail` field on the 201 response) | Adding an `email` parameter to `createBooking` (touches more surface for no benefit — the insert itself needs no email) |
| D-03 | The insert (US-007's `insertConfirmedBooking`) IS the commit point for a single-row Postgres write; the confirmation is sent immediately after `service.createBooking()` resolves `ok`, still inside the same request, awaited (not fire-and-forget) | Matches `app-architecture.md` §4.1 step 6 ("dispatch after commit, never inside it") without needing a queue or background worker this system deliberately does not have (`coding-standards.md`, "What this codebase does not have"). Awaiting keeps the request's outcome simple to test and reason about; `recordAndSend` never throws (US-034/AC-07), so awaiting cannot turn a good booking into a failed response | Fire-and-forget (`void recordAndSend(...)`) — saves a few ms of latency but loses the guarantee that the send was even attempted before the process could exit under a test or a fast redeploy, and this codebase has no background-job runner to hand it to |
| D-04 | `sendBookingConfirmation` is a thin, testable seam: `bookings.router.ts` receives a `notifications: NotificationsService`-shaped dependency (via `BookingsRouterDeps`, wired from a new `BuildAppOptions.notifications` test seam in `composition.ts`), matching the existing `availability`/`adminBookings`/`desks`/`users` seam pattern | `bookings.routes.spec.ts`'s existing `beforeEach` sets a `Config` fixture with no `MAIL_*` keys — the real `notificationsService` singleton would throw reading `config()` the moment any existing US-007 test hit `POST /api/bookings`. A seam lets those tests keep injecting a no-op fake, unchanged in behaviour, while new US-028 tests inject a controllable fake | Hard-wiring the real `notificationsService` import into the router (breaks every existing `POST /api/bookings` test that doesn't set mail config, and makes AC-07's "mail service unavailable" case untestable without a real transport) |
| D-05 | `bookings.router.ts`'s call to `notifications.sendBookingConfirmation` is wrapped in its own `try/catch`, logging and swallowing rather than trusting `recordAndSend`'s "never throws" contract from three files away | AC-07 ("the booking is not lost when the email fails") reads as a property this route holds, not only one a dependency happens to hold today; a future edit to `notifications.service.ts` that reintroduces a throw would otherwise turn every booking into a `500` the moment mail is unavailable | Trusting the contract with no local guard (fewer lines, but couples this route's correctness to an invariant it cannot see and does not own) |

Cite these as `US-028/D-01` outside this folder.
