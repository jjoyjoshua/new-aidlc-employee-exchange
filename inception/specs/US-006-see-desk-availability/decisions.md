# US-006 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision | Rationale | Alternatives rejected |
| ---- | -------- | --------- | ---------------------- |
| D-01 | AC-04's `.eq('is_active', true)` predicate is proven by a repository test over a recording fake Supabase client (`setSupabaseForTesting`), not by real-Postgres integration tests | Confirmed with the human at D1 (Architect design note §6, option B). Catches the realistic regression — the predicate dropped or inverted — with no new dependency and no CI infrastructure. Honest that it pins our intent, not Postgres's actual behaviour | Option A (stubs only + a manual check) — proves nothing about the predicate itself. Option C (Docker + Supabase local stack in CI) — the strongest proof, but a new dependency and CI machinery the human deferred to when it becomes mandatory at US-007, where the unique indexes are RISK-004's whole answer |
| D-02 | `officeDateSchema` itself gains a real-calendar-date check (`.refine`), applied everywhere it is used — requests and responses alike | Confirmed with the human at D1 (design note §2.2). `2026-02-30` matched the old regex, reached Postgres, and surfaced as an unhandled `500` — the first time a client-controlled date crosses the wire. One definition of "a valid office date" is worth more than two, and nothing legitimate (`officeToday`, the UI's own window) can ever produce an invalid one | A separate `officeDateRequestSchema`, applied only at route edges, leaving `officeSchema.today` as a bare shape-check. Rejected — it adds a second name for one concept and a rule every future route must remember to apply |
| D-03 | Both `desks` and `bookings` are created whole, with every constraint and index, in this story's two migrations — not deferred, not stubbed down to the columns a read needs | Design note §1.1. `bookings` created without its two partial unique indexes would mean US-007 retrofits RISK-004's entire answer onto rows that were never constrained by it, and any seeded row violating the invariant would then fail *US-007's* migration for a reason belonging to this story | Deferring `bookings` to US-007 and stubbing availability — makes US-006 UI-only with a fake and moves a schema review into the PR that also carries the booking concurrency design. A `bookings` table with only `desk_id`/`booking_date`/`status` — a materially different, unconstrained table |
| D-04 | The availability read is two explicit-column `SELECT`s (`desks`, then `bookings`), not one PostgREST embedded resource | Design note §2.8. The embed's `!inner` hint filters the *parent* rather than the *child*; getting the direction wrong silently inverts AC-03 (the response would contain only taken desks) while looking plausible in review. The saved round trip is not worth that risk on a ≤100-row table | `desks?select=id,desk_number,bookings(id)&is_active=eq.true&bookings.booking_date=eq.<date>&bookings.status=eq.confirmed` — rejected for the reason above |
| D-05 | Zone grouping (`groupByZone`) lives in `apps/ui/src/screens/book-a-desk/zones.ts`, screen-private, and is not added to `apps/api/src/domain/` or the wire contract | Design note §3.1, §2.4. Only the browser groups; a server-side grouping function nothing calls is dead code in the one place this codebase keeps rules findable. Zones are also a presentation decision still carrying an open research question (SCR-003:200) about whether the letters mean anything physically — baking them into the shared contract would make a UI experiment a contract change | Sending `zones: [{ zone, desks }]` from the server. Rejected — a second source of truth for a grouping the array already determines, and it moves a reversible UI decision onto a protected path |
| D-06 | AC-09 (no active desks) is checked as `desks.length === 0`, and that branch is written and tested to run **before** any fully-booked branch a later story adds | Design note §2.6. The two facts ("no desks exist" and "every desk is taken") are indistinguishable by a render that checks fully-booked first — it would show the wrong empty state to an office that has never had a desk, and pass any test that only exercises partial-booking data. This precedence is the actual defect risk, not the copy | No discriminator field on the wire (rejected as a second source of truth, per D-05's reasoning) — a server-sent `state` value could disagree with the array it describes |
| D-07 | Desks reach the database for local development via a deliberately-run `supabase/seed/desks.dev.sql`, outside `supabase/migrations/`, never executed automatically | Design note §5. The Supabase CLI here is linked to a hosted project with no `config.toml` and no local Docker stack, so `supabase db reset` (which would run the CLI's own `seed.sql`) is destructive against it. This file is named and commented to make clear nothing automated runs it, and it is deleted once US-017 (admin adds a desk) exists | Seed rows inside `0002_desks.sql` (puts dev fixtures into schema history and every environment). A `tools/seed-desks.mjs` script against the service-role key (a new script holding a production credential is an explicit escalate-don't-decide item, and it would duplicate the write path US-017 is about to build properly) |

| D-08 | `AuthContextValue` gains `api: ApiClient` — the exact same authenticated client `signIn`/`setPassword` already close over, now exposed for other screens to call | Not anticipated by the design note. Before this story, only `auth-context.tsx` itself ever called `/api/*`; US-006 is the first screen that needs an authenticated GET of its own, and there was no way to reach `accessTokenRef` (private to the provider) from outside it. Exposing the existing client is the minimal fix — a screen building its own `createApiClient` would either duplicate that ref or read a token that goes stale after sign-in | A second, screen-local `ApiClient` instance in `BookADesk`, reading the token some other way (e.g. from `localStorage` directly) — rejected, it duplicates state the provider already owns and would drift from it silently after a token refresh |

Cite these as `US-006/D-01` through `US-006/D-08` outside this folder.
