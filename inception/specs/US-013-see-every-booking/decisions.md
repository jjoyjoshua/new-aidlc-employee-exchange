# US-013 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision | Rationale | Alternatives rejected |
| ---- | -------- | --------- | ---------------------- |
| D-01 | Confirmed with the human: `total` (AC-07's count line) is the full count matching the view, not the number of rows currently loaded on screen | The count line's job is to state the query in prose so an occasional administrator trusts what they're looking at; a number that changes on every `Show more` press describes the page, not the query (design-note §2.5, open item 1) | The number currently loaded — rejected, it would read as the filter having changed every time `Show more` is pressed |
| D-02 | Confirmed with the human: the offset-vs-keyset pagination distinction is recorded as a criterion in `ai/standards/api-standards.md` §Pagination, not as a new ADR | The Architect's own test (does the decision bind work beyond this story with a rejected alternative a future author would relitigate — yes, but the criterion fits in two sentences and the standard already names this endpoint) applied; the human agreed (design-note §8, open item 3) | An ADR — rejected as more ceremony than two sentences in the document a future admin-list author will actually open |
| D-03 | Confirmed with the human: keep `.max(MAX_PAGE)` on the query schema | Cheap insurance against integer overflow in the offset arithmetic for a pathological `?page=` value, with no real downside (design-note §2.2, open item 6) | Drop it — rejected, no cost to keeping it |
| D-04 | The 360px skeleton row (`AdminSkeletonRow`) is built at **160px**, not the 188px SCR-005's component table states | SCR-005's 188px anticipates the cancellable-row variant (the taller of the two real card heights the Figma frames show: 188px with a Cancel button, 160px without). US-013 never renders a Cancel control (D-06/design-note §6.1), so every real 360px row in this story is the 160px shape — a skeleton at 188 would visibly shrink when data lands, which is exactly what "skeleton at real row height" (AC-09) exists to prevent. Confirmed against the real Figma frames: node `176:485` ("Row · A-01 Fri 4 Sep", no action) measures 160px; node `176:427` (with a Cancel button) measures 188px. Design-note open item 7, resolved by this reading rather than escalated — the frames are the tie-breaker the note itself named | 188px, matching SCR-005's prose exactly — rejected, it would mismatch this story's own real content and cause a layout shift on load |
| D-05 | AC-11's table↔card switch renders both DOM trees unconditionally and lets CSS (`display: none`/`block` at the 1024px breakpoint) show exactly one, rather than a `useMediaQuery` hook or overriding `display` on one `<table>` | Matches this codebase's zero-`matchMedia` precedent (every other responsive switch — the shell, the dialog, the account menu — is CSS-only) and is the only option provable in `jsdom`, which evaluates no media queries and performs no layout. Overriding `display` on a `<table>` drops its implicit ARIA roles in every major browser, silently breaking the semantics SCR-005 argues for at the one width the table exists (design-note §6.5) | A `useMediaQuery` hook — rejected, introduces the codebase's first JS breakpoint where a CSS one already works; `display: block` on the table — rejected, breaks table semantics |
| D-06 | No action/cancel column in any layout (table, 768 card, 360 card) — confirmed by the Architect | `BookingRow.tsx`'s own history: US-010 shipped zero action affordance, US-011 added `onCancel` later. AC-03 enumerates exactly four fields. The edge-case bullet about a non-cancellable row's reason text is a constraint on how US-015 renders, not an obligation to build the column's structure now — building an always-em-dash column with nothing behind it would ship dead UI (design-note §6.1) | Building the column now with a permanent em dash — rejected, communicates a falsehood (implies nothing is ever cancellable) and has no test that can fail until US-015 |
| D-07 | ST-03's empty state ships "Nobody has booked a desk yet." only — no conditional "Add desks so people can book" body/action — confirmed by the Architect | No desks admin endpoint exists yet to check whether the desk inventory is also empty; this codebase's own precedent (`routes.tsx`'s "a route with no screen behind it is a 404 that looks like a bug", applied identically in US-002 §6.1 for a Settings menu row) says don't build the conditional branch before its dependency exists. AC-08 only requires the empty state to say it is empty, which this meets in full (design-note §6.2, open item 4) | Building a desk-count check now — rejected, pulls a whole desks-admin capability into this story for one conditional sentence |
| D-08 | `AdminBookingsRepository` is a new, separate object in `modules/bookings`, not a 12th method on `AvailabilityRepository` — per the Architect's correction to my own initial proposal | Every existing method on `AvailabilityRepository` is desk-scoped or `user_id`-filtered; that is a cheap, checkable invariant this codebase leans on for its anti-enumeration guarantees (US-006/AC-06, US-007/D-03). `listAllBookings` is the first cross-employee read in the codebase, and a 12th method on that object would put an unscoped query one copy-paste away from a scoped one on the exact surface AC-10 protects (design-note §4.2) | A 12th method on `AvailabilityRepository` (my own original plan) — corrected by the Architect and accepted |
| D-09 | The FK ambiguity between `bookings.user_id` and `bookings.cancelled_by` (both referencing `user_profiles`) is resolved with PostgREST's column-based disambiguation, `user_profiles!user_id(full_name)`, not the Postgres-generated constraint name | The constraint name is auto-generated by Postgres and appears nowhere in this repository, so depending on it ties the query to a string nobody wrote down. `user_id` is the literal column name in the migration and is stable under this project's own rules (changing it is a migration, itself Complex). Verified against the recording-fake's limits: this is a runtime-only property the fake cannot prove, so it is also verified against real Postgres via the existing `RUN_BOOKINGS_CONCURRENCY_TEST=1` harness before merge (design-note §3.1) | Naming the FK constraint explicitly in a migration — rejected, a protected-path change for a query-string convenience; two round trips (page bookings, then fetch profiles by id) — rejected as the fallback, not the default: it re-solves a problem PostgREST already solves |

| D-10 | The repository maps PostgREST's `PGRST103` ("Requested range not satisfiable") to an empty page (`{ rows: [], total: 0 }`), rather than letting it throw | Verified against the real disposable Supabase project (design note open item 2): a page past the last matching row answers `PGRST103`, not the empty result the fake-client unit tests alone would suggest. Reachable legitimately (a tab open across office midnight, or a hand-typed `?page=`), and the honest answer is an empty page, not a `500` — the same discipline `insertConfirmedBooking` uses for its own recognised Postgres error codes | Letting it throw into a bare `500` — rejected, this is an expected condition, not a defect |

Cite these as `US-013/D-01` through `US-013/D-10` outside this folder.
