# US-020 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision           | Rationale                                        | Alternatives rejected                              |
| ---- | ------------------ | ------------------------------------------------ | -------------------------------------------------- |
| D-01 | Search is server-side: `GET /api/admin/users?q=<term>`, filtering via case-insensitive `ILIKE` over `full_name`/`email` at the repository layer | `inception/architecture/db-design.md:351` already states this as the approved implementation for REQ-032 ("left as a case-insensitive `LIKE` over `full_name` and `email` with no special index") — a Gate 1 architecture decision, not an open question. This supersedes the story's own "server-side or client-side as `/architect` decides" wording (`US-020-find-an-account.md:122`), which predates the db-design addendum | Client-side `Array.filter` over an already-fetched whole list (mirroring desks' `summaryLine` pattern, `apps/ui/src/screens/desks/copy.ts:52-57`) — this was DEV's first instinct and the task brief's own suggested default, but it would contradict written, approved architecture rather than resolve a genuinely open question |
| D-02 | The summary line's four counts (AC-02, AC-06) are computed by a dedicated whole-table read in the service, independent of `q`, never derived from the (possibly filtered) `users` array in the same response | D-01 makes the server-side, not the browser, the one place that ever holds the unfiltered set once a search is active — deriving the summary client-side (as desks' `summaryLine` does) would silently break AC-06 the moment `q` is non-empty, since the browser would no longer hold the whole list to derive it from | Client-side derivation from an unfiltered fetch, mirroring `US-016`'s `summaryLine` — rejected because it only works when the client holds the whole list, which D-01 does not guarantee under an active search; recomputing summary counts from the filtered result — rejected outright, since AC-06 explicitly forbids exactly that |
| D-03 | The four row-menu items (Edit, role change, Reset password, Deactivate/Activate) render as real, correctly labelled, disabled controls with an accessible reason, rather than being omitted until their destination stories land | AC-10 tests the menu's fixed structure, order, and labelling now; omitting the items would fail that AC rather than under-deliver it. This is `US-016/D-02`'s "visible-but-disabled unbuilt control" pattern applied verbatim — same reasoning `apps/ui/src/screens/desks/DeskInventoryRow.tsx`'s docblock (lines 13-19) records for its own now-superseded disabled state, and the same `title` + visually-hidden-span shape `AdminBookingRow.tsx:66` already uses for its own non-cancellable action | Omitting the four items until US-023–US-027 ship — rejected because AC-10 would then have nothing to test; a per-story-name reason ("Available once US-024 ships") — rejected for the reason `US-016/D-02` already gives: naming an internal story id to an administrator is jargon a screen must not surface |
| D-04 | `StatusChip` gains a new `kind: 'account'` member, not a reuse of `kind: 'inventory'` (US-016), with its own `ACCOUNT_LABEL` map (`{ active: 'Active', inactive: 'Deactivated' }`) bound to the SAME `.status-chip--active`/`.status-chip--inactive` CSS classes `kind: 'inventory'` already uses | AC-01 requires the word "Deactivated," not "Inactive" — a different lifecycle word for the same quiet-neutral visual treatment. `US-016/D-04` (`inception/specs/US-016-see-the-desk-inventory/decisions.md:10`) explicitly predicted this: "a future `kind: 'account'` chip with the same `status` values (SCR-008) is expected to land on the same classes... since it wants the same visual treatment." SCR-008's own designer handoff independently confirms it was built as a cloned `Deactivated` variant of the library's `Inactive` chip (`SCR-008-people.md:295-296`) | Reusing `kind: 'inventory'` with a parameter to override its label — rejected because `StatusChipProps` is a discriminated union keyed on fixed label maps (`LABEL`/`BOOKING_LABEL`/`INVENTORY_LABEL`), not parameterised copy, and threading a custom string through it breaks the "one word per kind" shape every existing variant keeps |
| D-05 | The row menu (AC-10, AC-11) is a new, screen-private component — an anchored, **unscrimmed** popover at ≥768px and a scrimmed bottom sheet titled with the account's name at 360px — built independently of `Dialog` (`apps/ui/src/components/dialog/Dialog.tsx`) | `Dialog`'s own docblock (`Dialog.tsx:11-14`) states it owns "the scrim overlay, the mobile-first bottom-sheet/centred-card treatment" at every width — always scrimmed, always modal. SCR-008 ST-15's structural decision (`SCR-008-people.md:252`) is the opposite at desktop: "an anchored popover is not [a modal]... it hangs off the `⋯` it came from... so it needs no dimming." No existing component in `apps/ui/src/components/` matches that shape (verified: only `Dialog`/`ConfirmDialog` exist there) | Composing `Dialog` with `role` widened to cover an unscrimmed variant — rejected because scrimming is currently unconditional inside `Dialog`, and threading a `scrim?: boolean` prop through its centred-card/bottom-sheet logic is exactly the kind of shape change the Architect design note should evaluate, not something DEV should improvise into a shared component |
| D-06 | The new endpoint is `GET /api/admin/users` (not `/api/admin/people`) | Matches this codebase's existing convention that a route segment equals its owning module's folder name (`desks` → `modules/desks`, `bookings` → `modules/bookings`; `admin.router.ts:98,121,154,190,221`). The module is named `users` (`apps/api/src/modules/README.md:9`, `eslint.config.mjs:16-22`), so the endpoint follows that name even though the UI's own route and nav label are "People" (`AppShell.tsx:34`) | `/api/admin/people` — rejected to keep the API path aligned with the module it lives in rather than the screen's display name; the same asymmetry already exists internally between `kind: 'inventory'` and the displayed word "Active"/"Inactive" |
| D-07 | Default ordering is `full_name` ASC (citext, case-insensitive collation) | No AC or SCR-008 frame states an explicit order; `full_name` is one of the two columns REQ-032 searches, and alphabetical-by-name is the least surprising default for a screen whose primary control is a name/email search | Ordering by `is_active DESC, role` (mirroring the index `user_profiles_is_active_role_idx`'s column order) — considered because the index literally serves this read, but rejected as a default since grouping by activity/role first, then presumably by name within each group, is not stated anywhere and would need its own tie-breaker decision; flagged as an open, non-blocking question in `implementation-plan.md` |

Cite these as `US-020/D-01` outside this folder.

## Architect review note (2026-09-19)

D-01, D-02, D-04, D-05 and D-06 above are confirmed as written by `design-note.md`. **D-03 is
refined, not confirmed**: the design note requires the four menu items to be `aria-disabled` and
focusable rather than carrying the HTML `disabled` attribute this entry originally specified —
applying `US-016/D-02`'s pattern verbatim to a menu (rather than a table row) leaves nothing
focusable inside it, which breaks AC-12 and AC-10's accessible half. See `design-note.md` §6 for
the full reasoning and `ADR-010-unbuilt-destination-controls.md` for the durable rule this
correction is promoted into. This entry is left as originally written for the historical record;
the corrected pattern is what `implementation-plan.md` Step 11 now builds.
