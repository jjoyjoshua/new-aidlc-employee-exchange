# US-012 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision | Rationale | Alternatives rejected |
| ---- | -------- | --------- | ---------------------- |
| D-01 | Scope AC-06 to SCR-002 (My bookings) only; SCR-005 (All bookings) is a tracked follow-up | `AllBookings.tsx` is a stub with no list yet (US-013's scope) — there is nothing on that screen to refresh. Confirmed with the human before planning. | Building a minimal real list on SCR-005 now to satisfy AC-06 in full — rejected as pulling US-013/014/015 scope into a 3-point Should; sending the story back to BA — rejected since the AC is satisfiable in full once US-013 lands, not defective |
| D-02 | Detect "regained focus" via both `document` `visibilitychange` (→ `'visible'`) and `window` `focus`, coalesced so the same regain fires subscribers once. **Superseded in placement, not reasoning, by [ADR-008](../../../knowledge/decisions/ADR-008-focus-refresh-shared-module.md): this logic now lives once in `apps/ui/src/lib/data-refresh.ts`, not in a per-screen hook.** | Neither event alone is reliable across browsers: `visibilitychange` misses the case where the tab was always the frontmost tab but the OS-level window lost and regained focus; a bare `focus` listener misses a background-tab-to-foreground-tab switch within the same window. Coalescing via a microtask-reset flag absorbs the common case where both fire for the same regain, while still letting two genuinely separate rapid regains each fire (the story's own "rapid focus changes" edge case). `ai/standards/task-surfaces.md:61-64` and `apps/ui/src/lib/README.md:6-8` require this to be one app-wide module, not a per-screen `useEffect` — the reason the original per-screen version was halted | `visibilitychange` alone — rejected, misses the OS-focus case; a fixed-interval throttle (e.g. 500ms) — rejected as an invented business rule the story explicitly leaves to judgment, and a microtask coalesce is exact rather than a heuristic window; a per-screen hook — rejected by ADR-008, see there for the full alternatives table |
| D-03 | The quiet refresh re-fetches only the default (first) page and merges it into `items` by `id` — updating fields of known rows, prepending unseen ones — without touching `nextBefore` or any page already loaded via `loadOlder()` | `retry()` (US-010) intentionally drops accumulated older pages, which is safe there because it also re-enters `status: 'loading'` and the whole view resets. AC-03 forbids exactly that reset ("no layout shift", scroll kept) for this refresh, so dropping older pages here would cut off content the employee is actively reading. Merging by `id` is safe because a booking's status change (AC-02's whole point) never moves it into a different page — sectioning and the wire's date-DESC order are driven by `status`/`date`, neither of which a cancellation changes (ADR-007) | Re-fetching and replacing the entire accumulated list (all loaded pages) on every quiet refresh — rejected as unbounded request cost for a background check, and reintroduces the "which page is `nextBefore` now" ambiguity D-03 avoids; leaving `nextBefore` update to the fresh page-1 response — rejected, it would rewind the cursor behind pages the employee already loaded |
| D-04 | A failed quiet refresh is surfaced with the existing `Alert` component at `tone="warning"`, alongside a **Retry** button, rendered inline above the list rather than replacing it | Reuses an existing component with props already in its scope (`tone`, `actions`, `live`) — no new prop, so this stays inside the Medium-tier UI carve-out ("a change inside one component that keeps its props and events"). `role="alert"`/`aria-live="assertive"` already gives AC-04's "reported… with a retry" an accessible announcement for free | A silent/no-UI failure — rejected, AC-04 requires the failure be reported; a toast — rejected, `Toast` in this codebase has no dismiss and is reserved for one-per-page-visit navigation confirmations (design note precedent in `MyBookings.tsx`), not a recurring background-refresh notice |
| D-05 | Suppress `useFocusRefresh` entirely (pass `enabled: false`) whenever the cancel dialog is open, rather than letting it fire and reconciling state around an open dialog | The dialog's own state (`use-cancel-dialog.ts`) holds a copy of the target item, so a background refresh wouldn't corrupt it directly — but "must never pull the row out from under a confirmation" (AC-05) is satisfied unconditionally by not running the refresh at all during that window, which is simpler to reason about and to test than proving every interleaving is safe | Letting the refresh run and diffing whether the dialog's item was affected — rejected as materially more complex for no behaviour the story asks for (no AC requires the list to update while the dialog is open) |

Cite these as `US-012/D-01` through `US-012/D-05` outside this folder.
