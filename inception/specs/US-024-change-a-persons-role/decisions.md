# US-024 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision | Rationale | Alternatives rejected |
| ---- | -------- | --------- | ----------------------- |
| D-01 | On SCR-009's edit form, when both the role and the name/email change together, the role change is submitted **first** (`POST .../role`); the name/email `PATCH` only follows if the role change succeeded or the role was unchanged | AC-08's edge case requires that a blocked role change leave the rest of the form "still saveable" and untouched. Submitting role first means a `blocked` outcome never reaches the `PATCH` at all — nothing has been saved, matching ST-05's copy exactly. The reverse order (details first) would sometimes leave a name/email change already committed while the role change fails, which the current ST-05/ST-08 copy has no sentence for | Submitting both in parallel — rejected: a partial success (details saved, role blocked) has no approved copy and would need a new dialog state nothing in SCR-009 describes. A single combined endpoint — rejected: role is a refusable business-rule transition (BR-001.11) and details is a plain field update; `ai/standards/api-standards.md`'s own split between `PATCH` and a verb sub-resource argues against merging them |
| D-02 | The acting administrator's own role change patches `useAuth()`'s local `user.role` directly, on the success callback, rather than re-fetching `GET /api/auth/session` | The story's edge case requires the effect to be immediate ("They lose the admin screens immediately"), and the success response of the role-change call already carries the new role — a second round trip would add latency and a second place this could fail for no benefit. This stays a UI decision rather than a trust decision precisely because `require-admin.ts` re-reads `role` fresh from `user_profiles` on every server request, never from a JWT claim (design note §4.4) — the local patch can only change what the browser *renders*, never what the server *permits* | Re-fetching the session on every role-change success — rejected as unnecessary network traffic for a fact the response already states; a page reload — rejected, it is the one thing REQ-004's "no voluntary re-authentication" spirit (BRD-001 §10, applied by analogy) argues against for a routine admin action |
| D-03 | The last-admin refusal (`last_active_admin`) carries no `details` payload — the server sends only the code, and the browser composes ST-07/ST-09's exact sentence from the account row it already holds (the acting admin's own name, from `useAuth()`) | Unlike US-019's `desk_has_upcoming_bookings` (ADR-009's `details.upcomingBookings`), every fact ST-09's sentence needs — the account's name, that it is the "only active admin" — is already on the browser's own screen before the request is even sent. The refusal **code itself is the assertion**: the People summary line's admin count is not BR-001.11's own count (it includes deactivated admins; `users.service.ts`'s `tallySummary`), so the browser cannot predict the refusal from anything it already holds — only the server's `last_active_admin` code tells it the rule actually fired (design note §4.3, correcting this rationale from "the caller already knows the fact" to "the caller already knows the name; the code supplies the fact") | A `details: { fullName }` payload mirroring `desk_has_upcoming_bookings` — rejected as redundant: the caller already knows which account it just tried to change |
| D-04 | **Residual, routed to the human as a change-request (design note §6.1, open item 2; [`jjoyjoshua/new-aidlc-employee-exchange#57`](https://github.com/jjoyjoshua/new-aidlc-employee-exchange/issues/57)):** if the edit form's role change succeeds but the following name/email `PATCH` then fails, the account is left with its **new role** and its **old** name/email, while SCR-009 ST-08's approved copy says "Nothing has changed." That sentence is false on this one path. Ships as-is (approved copy, unchanged) for this PR; issue #57 tracks the fix | ADR-012 was written for the identical shape one level down (two systems, one write each, no shared transaction); this is the same shape one level up, between two endpoints. Three options were put to the human (state the partial outcome in new copy; compensate by reverting the role, itself refusable by BR-001.11; or route both fields through one request, which contradicts SCR-009 ST-05's approved in-form refusal). **Decided 2026-09-20 (Joy Joshua): file the change-request, ship without a fix for now** | The other two options (compensating revert; single combined request) — not chosen |
