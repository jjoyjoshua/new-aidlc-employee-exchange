# US-023 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision           | Rationale                                        | Alternatives rejected                              |
| ---- | ------------------ | ------------------------------------------------ | -------------------------------------------------- |
| D-01 | `findByEmail` gains an optional second `excludeId` param rather than a new method | Same query, one extra `.neq('id', excludeId)` clause when present. Both existing callers (`users.service.ts:116,128`, US-021's create flow) omit it and are unaffected — additive, not a breaking signature change | A second `findByEmailExcluding` method — two near-identical queries to keep in sync for no behavioural gain |
| D-02 | The read-then-write window between `findById` and the compensating restore (design-note.md §2.6) is accepted and logged, not closed with an optimistic-concurrency guard | No story describes two administrators editing one account concurrently, and US-018 shipped the identical exposure on desk numbers unguarded. ADR-012's own alternatives table names the one-line guard and defers it until a story asks | `.eq('email', oldEmail)` on the compensating update — closes the window in one line, but adds a refusal state (a third administrator's edit lost silently) that no approved screen has copy for |
| D-03 | `markUpdated` reuses the `byFullName` comparator already at `use-users.ts:38` to re-sort after replacing the row, rather than re-fetching the list | A name change can move the row in a `full_name` ASC list; re-sorting client-side with the same comparator the initial fetch and `markAdded` already use keeps one sort order across the whole screen. Consistent with US-021's own fix for `markAdded` | A full re-fetch after every edit — correct, but throws away the optimistic update AC-08's guard already produced and adds a network round trip with no AC asking for it |
| D-04 | `apps/ui/src/lib/update-account.ts` is a new file, mirroring `rename-desk.ts`'s shape (PATCH, parse `200` through the existing response schema) plus `create-account.ts`'s `details`-parsing for the duplicate case | Two established precedents in this codebase for the two halves of this fetcher's job; combining them is the smallest diff that stays consistent with both | Extending `create-account.ts` with a `mode` parameter — conflates two different HTTP methods and two different outcome shapes (create has no `not_found`) in one file |
| D-05 | `RadioGroup` gets a new `aria-disabled?: boolean` prop, defaulting to `false`, additive to (not replacing) its existing `disabled` prop | Keeps every existing create-mode caller's behaviour byte-for-byte (native `disabled`, unchanged), while giving edit mode the ADR-010-compliant path the design note requires (§4.3) | Replacing `disabled` with a single prop that always renders `aria-disabled` — would silently change create mode's behaviour too, which no AC for this story asks for |
| D-06 | AC-06 is proven by asserting `user_profiles.email` holds the new value after a successful update, plus a one-line constraint added to `users/README.md` binding future notification code to read the account's current email — not by an end-to-end test that sends and inspects a notification | `apps/api/src/modules/notifications/` contains only a README; no notification code exists to observe. A test claiming to prove AC-06 end-to-end would be asserting against code that isn't there | Writing a fake notification-sending stub just to give AC-06 an observable test — invents a surface this story does not need and a future story would have to reconcile with the real implementation |
| D-07 | The browser folds a `404 user_not_found`, a `503 service_unavailable`, and a bare `500` all into the same `failed` outcome → ST-08 | No approved SCR-009 copy exists for "that person is gone" as a distinct state, and `rename-desk.ts:18-19` already folds `desk_not_found` the same way for the identical reason | A dedicated "account no longer exists" UI state — a real gap (the row could vanish between page-load and save if another tab deactivates or the account is later deleted), but no story or screen spec asks for it this release |

Cite these as `US-023/D-01` etc. outside this folder.
