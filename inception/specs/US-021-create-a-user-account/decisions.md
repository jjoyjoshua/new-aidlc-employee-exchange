# US-021 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision                                                                                                       | Rationale                                                                                                                                                                                                                                                                                     | Alternatives rejected                                                                                                                                              |
| ---- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-01 | Email normalisation (`trim().toLowerCase()`) lives in `createAccountRequestSchema`'s own `.transform`, not in the service | The parsed value is both what the duplicate check reads and what gets stored — `deskNumberSchema` already establishes this exact shape for desk numbers (`libs/contracts/src/desks.ts:98-104`), and it removes the second place a normalisation step could be forgotten                        | Normalising explicitly in `users.service.ts`, mirroring `auth.service.ts:127`. That precedent never persists the typed email (sign-in only compares it); this story stores it, which is what the desk-number precedent actually matches |
| D-02 | Duplicate detection reads `user_profiles` directly (`findByEmail`, exact `citext` match) before writing to Supabase Auth. **Corrected by the Architect's design note (§2.7): this is a message-composition read, NOT the uniqueness arbiter.** Two indexes actually arbitrate a real race — GoTrue's own uniqueness on `auth.users.email` (which fires first, being the second write when a race occurs) and `user_profiles_email_key` — the same property `desks.repository.ts:56-58` states for `insertDesk` and the same reason that file refuses a pre-check for uniqueness | The result must name the colliding account and say whether it is deactivated (AC-06, ST-04) — information neither index's own violation error carries. The read is for the MESSAGE, never for correctness under concurrency; `users.service.ts`'s `createAccount` re-reads `findByEmail` a second time on a race-`duplicate` from the adapter for exactly this reason (design note §2.4, A1) | Attempting `auth.admin.createUser` first and parsing its duplicate error. The refusal copy would still need a `user_profiles` read to name the holder, so nothing is saved by trying Auth first. Treating this read as sufficient on its own to prevent a duplicate — it is not; see the design note §2.7 |
| D-03 | `RadioGroup`/`RadioOption` built **screen-private**, under `apps/ui/src/screens/people/`, not `apps/ui/src/components/`. **Refined by the Architect's design note (§4.4): the original wording below was wrong to treat SCR-009's "no new component is needed" as a statement about this codebase's React tree — it is a statement about the Figma library, where the component already exists.** This project's own extraction bar is two real consumers (`components/README.md:6-7`); US-024's presumed second consumer is most likely the same file (`UserFormDialog` gaining an edit mode), not a second one | A component in `apps/ui/src/components/` carries a public-props contract that is Complex to change on its own (`ai/standards/task-surfaces.md`). Building it screen-private defers that cost until a genuine second screen needs the control, which is when it earns extraction | ~~A component private to `screens/people/`~~ (this is now the decision, not the rejected alternative). Building it in `components/` on the strength of the design doc's Figma-library reference alone — corrected above |
| D-04 | Password generation is one pure function, `apps/ui/src/lib/generate-password.ts`, that self-verifies its output against `evaluatePasswordPolicy` before returning | REQ-033/V-18 requires every generated value to satisfy V-12 and avoid `1`/`l`/`I`/`0`/`O`; self-verifying against the same function the checklist uses means the generator and the policy cannot silently drift apart, the same "one function, not two" reasoning `password.ts`'s own docblock states for `newPasswordSchema` | Building the character set once and trusting it by construction. Slightly cheaper, and it is exactly the kind of implicit invariant that breaks quietly if the excluded-character set is ever edited without re-deriving the guarantee |
| D-05 | The BROWSER-facing outcome (`create-account.ts`'s `CreateAccountOutcome`) stays three kinds (`ok` / `duplicate` / `failed`), mirroring `AddDeskOutcome`, never surfacing "which of the two writes failed" or "was Auth reachable at all" to the UI. The SERVICE's own internal outcome is wider (`ok` / `duplicate` / `unavailable` / `failed` — D-09) so the router can choose the right HTTP status; that widening stops at the service/router boundary | The administrator never needs to see the distinction — AC-11 already requires a failure to look like "nothing was created," regardless of cause. The operator DOES need it, which is what D-09's status split is for | A fourth outcome kind surfaced all the way to the browser. It would leak a two-systems implementation detail into the UI contract for no behaviour the spec asks for |
| D-06 | The Supabase Auth call for creating a credential lives in a **new** `apps/api/src/modules/users/users.adapter.ts`, not in or reused from `auth/auth.adapter.ts` | `eslint.config.mjs:16-22` enforces `MAY_IMPORT.users = ['notifications']` — `modules/users` importing `modules/auth` is a build-time error, not a style preference. The new adapter calls `infra/supabase` directly, the same layer `auth.adapter.ts` itself calls, so no boundary is crossed | Importing `auth.adapter.ts`'s `createAccount` from `users.service.ts`. Fails lint immediately; the fix is not a decision, it is following an already-enforced rule. Loosening `eslint.config.mjs` itself. That file is a protected path — any change to it is Complex on its own, and the architecture doc's reasoning for the boundary (`app-architecture.md` §3) is not this story's to revisit |

| D-07 | `PasswordField` gains an optional controlled `visible`/`onVisibleChange` pair, alongside its existing uncontrolled default | Discovered during implementation: `PasswordField`'s show/hide state was fully internal (`useState` with no external access), so nothing outside it could force the field revealed. ST-09 requires exactly that — **Suggest a password** must reveal the generated value immediately, from OUTSIDE the field, on a value the field's own toggle never produced. Every existing caller (`SetPassword.tsx`) omits both new props and keeps its original always-starts-hidden behaviour, verified unchanged by the existing `PasswordField.spec.tsx` suite | A second, SCR-009-only password input built from `TextField` directly, duplicating the toggle `PasswordField` already has. Rejected — the whole point of `PasswordField` existing is that both password screens share one implementation |

| D-08 | The duplicate refusal carries `details: { fullName, isActive }` via a new `emailTakenDetailsSchema`, composed into copy client-side in `screens/people/copy.ts` — never a pre-composed sentence from the server | ADR-009's second application (design note §3.1): SCR-009's approved copy bolds the email inside the sentence and the field carries its own short message; composing that server-side means either losing the emphasis or regex-parsing prose back out of it, ADR-009's two already-rejected options. `conflict()` gains the same optional `details` parameter `unprocessable()` already has | A server-composed `message` string, as originally planned (Step 9's prior wording cited a non-existent `apps/ui/src/lib/errors.ts` for this — corrected). Rejected per ADR-009 |
| D-09 | The two server-side failure causes are distinguished by status: an unreachable Supabase Auth (`unavailable`) → `503 service_unavailable`; a `user_profiles` insert failure after compensation → a bare `500` | `http/errors.ts` already exists to let an operator tell "our dependency is down" from "our own defect" apart (US-001/AC-07's own reasoning, applied here a second time); no new error code, and the browser is unaffected either way — `create-account.ts` maps anything that is not `email_taken` to `failed` | One undifferentiated 500 for both causes. Cheaper, and it throws away the one signal that tells an operator whether the incident is "Supabase is down" or "our own code broke" |

| D-10 | `Dialog`'s shared CSS (`components/dialog/dialog.css`) gains a `max-height` cap and a scrolling `.dialog__body`, with the header/footer pinned (`flex-shrink: 0`) | Found by manual testing (the human ran the built form): SCR-009's form is the first dialog tall enough to exceed the viewport, and `.dialog` had no height cap at all — the header rendered above the visible viewport and the footer below it, with no scrollbar, on every width. Measured before fixing: dialog height 776px in a 607px viewport, top at -84px. This is exactly the "capped to the viewport, body scrolls" behaviour SCR-007/SCR-009's own design notes already specify; the shared component simply never implemented it because no dialog before this story's needed it | A per-screen override in `UserFormDialog`'s own CSS. Rejected — the missing behaviour belongs to the shared shell every dialog composes, and future tall forms (US-023's edit mode) need it too |
| D-11 | `Alert`'s `.alert__title`/`.alert__message` (both `<p>` elements) get an explicit `margin: 0` | Found by the same manual test: the browser's default paragraph margin (`14px 0`) pushed the message text down relative to its icon on every `Alert` in the app — verified by measuring `icon.top` vs `message.top`, a 14px gap matching the default `<p>` margin exactly. Pre-existing in the shared component, surfaced here because this story is the first to stack three `Alert`s in one form | Overriding it locally per alert instance. Rejected — the same shared-component reasoning as D-10 |
| D-12 | `apps/ui/src/screens/people/user-form.css` gives `#user-form` an explicit `display: flex; flex-direction: column; gap: var(--s-16)` | Found by the same manual test: `Dialog.tsx`'s `.dialog__body` only spaces its OWN direct children (the alerts and the one `<form>`), so nothing spaced the form's OWN children — they sat flush against each other with zero gap (`getComputedStyle(form).gap === 'normal'`, verified) until this rule existed. `DeskFormDialog`'s own form never needed this because it has exactly one field | Adding the gap to `.dialog__body` itself. Rejected — that would also add unwanted spacing between the alerts and the form, which are meant to sit close per SCR-007/SCR-009's own layout |

Cite these as `US-021/D-01` (etc.) outside this folder.

**Routed to the Architect and resolved: `ADR-011-cross-system-write-compensation.md` (proposed).** What the server does when the Auth user is created but the `user_profiles` insert then fails — order forced by the foreign key, compensating hard-delete on failure, logged and never surfaced to the caller, no cross-request self-healing. See the design note (`design-note.md`) §2 and §7 for the full reasoning.
