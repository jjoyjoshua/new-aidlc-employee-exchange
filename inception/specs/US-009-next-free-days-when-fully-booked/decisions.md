# US-009 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision | Rationale | Alternatives rejected |
| ---- | -------- | --------- | ---------------------- |
| D-01 | Build the multi-date lookahead rather than take REQ-035's stated fallback ("Try another day", no suggestions) | Confirmed with the human at Gate D1, on the Architect's recommendation (`design-note.md` §1): the lookahead costs two extra indexed queries, run only in the fully-booked branch, over indexes the schema already has (`0003_bookings.sql:77-78`). The `desks` table is not re-read — the availability call's existing read is reused in memory. Nothing in this shape grows with the window's length or is paid on the ~99% of requests that are not fully booked | The fallback itself — genuinely satisfies REQ-035 as written, and was rejected only because the measured cost of the real thing turned out to be small, not because the fallback would have been dishonest (`design-note.md` §6) |
| D-02 | `nextFreeDays` carries only dates, no free-desk count per suggestion — even though the approved Figma frame for ST-04 (node `39:1245`) shows one ("Thu 10 Sep · 12 free") | Confirmed with the human at Gate D1, after opening the real frame and finding this mismatch (the Architect's design note, written without opening Figma, argued against a count on the same staleness grounds this decision follows). A suggested day's free count can go stale between being suggested and being clicked — the same class of staleness the story's own Edge cases already accept for the date itself. A `change-request` issue is filed after this PR to correct the frame/spec, not the code | Widening the contract to `[{date, freeCount}]` to match the frame exactly — rejected: it would ship a number that can be wrong by the time it's read, for a UI detail the human chose not to keep |
| D-03 | The lead-line text above the suggestions is keyed on the count: the frame's exact wording ("The next two working days with desks free:") only when there are exactly 2; "The next working day with a desk free:" for exactly 1; no lead line at all for 0 — only the title and "Pick another date" | AC-05 requires the message to "still read correctly with no empty slot or placeholder" at every count, and the approved frame's line names "two" explicitly, which would be false when only one or zero days are offered. Confirmed with the human at Gate D1 | Always showing the frame's fixed "two" line regardless of count — rejected, it reads as wrong on the very case AC-05 exists to cover |
| D-04 | The "Pick another date" link inside the ST-04 card (found in the real Figma frame, not in the story text or the Architect's design note, which did not open Figma) calls the same picker-opening handler `DateStrip`'s existing "Pick another date" control uses (`setPickerOpen(true)` in `BookADesk.tsx`), rather than a new handler or component | It is the same action rendered a second time in a different location on the same screen — matching behaviour means matching implementation. `Button variant="ghost"` already exists and matches the frame's `Type=Ghost` styling exactly | A separate callback or a distinct "jump to calendar" affordance — rejected as unneeded generality for a control that does the same thing as one already on screen |
| D-05 | `EmptyState.body` becomes optional (`body?: string`) rather than adding a second component or a `body: string \| null` | US-009's zero-suggestion case has no body text to show at all — only a title and the "Pick another date" link. An optional prop is the smallest change that admits this, and ST-05's existing call site is unaffected (it always passes `body`) | A `FullyBookedEmptyState` variant component — rejected, the component's whole point (per its own docblock and the Architect's design note §4.4) is three contexts sharing one layout |
| D-06 | Suggestion buttons show a short visible label (`formatOfficeDateLabel`, e.g. "Thu 10 Sep") with a long-form `aria-label` ("Book a desk on Thursday 10 September"), following the pattern the Architect's design note recommended (§4.5) even though it was written before the frame confirmed the exact visible text | Consistent with `AvailabilityCount`'s established split between a short visible line and an unambiguous accessible name (US-006 design note §4.3) | A single long-form visible label — rejected, it does not match the frame's short chip text |

| D-07 | The ST-04 (fully booked) branch only renders when `!confirmFailure` — a desk-just-taken or ambiguous-failure alert (US-007/AC-08, AC-10) suppresses it even if the refetched list happens to be fully booked | Discovered during implementation, not anticipated by any story or the design note: `BookADesk.spec.tsx`'s existing US-007/AC-08 test refetches a single-desk office down to zero free desks after a conflict, and US-007's alert lives inside the ordinary-list branch. Without this guard, the new ST-04 branch would intercept that render and silently drop the alert, breaking an already-approved, already-tested AC. Gating on `confirmFailure` (only ever set by `handleConfirm`, cleared on the next date/desk change) preserves US-007's exact prior behaviour and adds nothing untested: an ordinary fully-booked load (no confirm attempt in flight) is unaffected | Letting ST-04 win regardless — rejected, it silently regresses US-007/AC-08 and AC-10, both already merged and tested; no story asks for the combined "just-taken alert + suggestions" state, so building it would be improvised scope, not a documented requirement |

Cite these as `US-009/D-01` through `US-009/D-07` outside this folder.
