# US-004 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision                                                                                     | Rationale                                                                                                                                                                                                                                     | Alternatives rejected                                                                                                                                                       |
| ---- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-01 | `POST /api/auth/set-password` — a third verb beside `/sign-in` and `/sign-out`                  | Adopted from the design note §2.1: the auth surface reads as three actions a person performs, and `/set-password` is already reserved on the client (US-001 note §9.1)                                                                        | `PUT /api/auth/password` — implies a `GET`-able resource, which this is not. `POST /api/auth/password-change` — same shape, no client/server mirror                       |
| D-02 | `confirmPassword` never crosses the wire — the request body is `{ newPassword }` only            | Adopted from the design note §2.2: the confirm field protects against a mistyped password, a guarantee the server cannot improve on; sending both doubles the plaintext copies of a credential in the request for no additional protection    | Send both and re-check equality server-side — looks like defence in depth, is not; adds a `400` with no `ST-##` behind it                                                  |
| D-03 | The step-5 password-change exemption is a **required constructor argument** (`'enforced' \| 'exempt'`) on `requireSession`, chosen by name at `composition.ts`, never a route-string comparison | Adopted from the design note §4.2: US-002 §2.2 already documented the `req.path`/`req.originalUrl` footgun under an `/api/auth` mount; a required argument fails at compile time rather than silently exempting nothing or too much           | An allowlist of paths inside step 5 — the exact footgun above. A separate `requirePasswordChanged` middleware composed after `requireSession` — reads `req.user` and creates a mount-ordering hazard that does not otherwise exist |
| D-04 | `GET /api/auth/session` also runs the **exempt** chain instance, alongside `POST /set-password`  | A finding surfaced in design note §4.3: `app-architecture.md` §5.1 named only two exemptions, but a mark-set account's cold-boot rehydration calls `/session` before it can render SCR-010; gating it means `auth-context.tsx`'s existing error-handling branch signs the user out instead of returning them to the password screen, breaking AC-08. `app-architecture.md` §5.1 is corrected in this PR to name three exemptions | Treating a `403` from `/session` as a signed-in state in the browser — cannot work, the fixed error shape carries no user or role                                          |
| D-05 | On a successful password change, no session other than the caller's own is revoked — no `'global'`, no `'others'` | **Confirmed with the human at Gate D1.** BR-001.17's full text says only that the mark clears and the administrator-set password stops working; it says nothing about other devices. The caller's own session must survive regardless (AC-07) | Revoking `'others'` on success — a defensible security instinct, but new scope BR-001.17 does not ask for; would need a `change-request` if wanted later                    |
| D-06 | Password-handling constraints for this story's three new plaintext-password paths, confirmed as hard requirements: (1) the request body is never logged, (2) `400` responses carry no issue list and never echo the value, (3) probe failures log a status and message only, never the candidate, (4) `confirmPassword` never crosses the wire (D-02), (5) no password reaches `decisions.md`, a committed test fixture, or a PR evidence paste | **Confirmed with the human at Gate D1**, per `ai/standards/task-surfaces.md` `§Escalate` — this is RISK-005's mitigation ("no password in persistent audit log") meeting its first piece of code | Logging request bodies for debugging — standard elsewhere, explicitly excluded here because the field is a live credential                                                |
| D-07 | The V-15 probe's successful session is revoked with scope **`'local'`**, never `'global'`        | The probe's JWT belongs to the session the probe itself just created; `'local'` ends only that session. `'global'` would also end the user's live session on SCR-010, signing them out mid-flow as a side effect of a validation failure and preventing ST-03 from ever rendering (design note §5.1) | `'global'`, matching the sibling call site in `attemptSignIn` — that site revokes a session belonging to an account just refused sign-in; this one revokes a session belonging to an account currently mid-task, which is the opposite situation |
| D-08 | Write order: the credential is set first (`auth.admin.updateUserById`), the `must_change_password` flag is cleared second — never the reverse | The only ordering under which every partial failure is recoverable (design note §6.1–§6.2). If the mark-clear fails after a successful credential write, the account is merely sent back to SCR-010 on its next request; if the order were reversed and the credential write failed, the account would be released into the product with the administrator-set password still live and the mark permanently cleared — REQ-029 silently defeated | Clearing the mark first — "tidier" in code, but the failure mode is unrecoverable and invisible                                                                            |
| D-09 | Two V-12 definitions proceeded under a stated assumption, not blocking code: "a special character" is any character outside `A–Z`/`a–z`/`0–9` (not an explicit allowlist); length is counted in UTF-16 code units (`String.length`) | An open allowlist can only ever help someone satisfy the rule; an explicit allowlist would refuse a legitimate character (e.g. `£`, `—`) with no way for the user to learn why. UTF-16 counting is what the underlying primitives (`String.length`, Zod's `.min`) already do | An explicit special-character allowlist (`!@#$%^&*`) — narrower than V-12's own wording and untestable against every keyboard. A grapheme-aware length counter — solves a problem nobody has raised and changes the policy quietly |
| D-10 | No new ADR for the V-15 probe-and-revoke mechanism or for the step-5 gate                        | Both are accepted architecture already: `app-architecture.md` §5.1 fixes the V-15 mechanism in one sentence, and the gate itself is `require-session.ts`'s own named seam. Supabase exposes no password-comparison API, so there is no real alternative to reject for the probe (design note §8) | An ADR documenting the probe — would document a decision already taken and written down elsewhere, which is not what an ADR is for in this repository                       |
| D-11 | `TextField` gains an `invalid?: boolean` prop, separate from `error`, so a field can take the invalid border/ring with no message of its own | SCR-010 ST-02 requires the new-password field to switch to its blocking look while the policy checklist beside it — not a second field-level sentence — carries the explanation; `error`'s presence coupled both the styling and the message, and the two needed to separate for this field alone. Additive and backward compatible: every existing caller passes `error` only, and `invalid` defaults to unset | A second, near-duplicate field component just for this screen — the edge, radius and focus ring are shared with every other text field, and forking them risks the two drifting apart over time |
| D-12 | Design note §6.4's open question is answered: **the caller's access token does not survive `auth.admin.updateUserById`.** Confirmed 2026-09-18 with a live check against this project's actual Supabase instance (create a throwaway user, sign in, call the exact admin write `auth.adapter.ts` makes, then retry `getUser` with the same token — it came back revoked). The specified fallback is implemented: `POST /set-password` now re-signs in with the new password after the write and returns `{ user, session? }`; the browser stores that session exactly as `signIn` does. `setPasswordResponseSchema` changed from an alias of `sessionResponseSchema` to its own shape with an optional `session` | This was the one item in the design note that could not be settled by reading code — an empirical fact about the installed Supabase project, not a design choice. Now that it is known, building for the alternative (assuming the token survives) would have shipped a story that passes every test over a stub and fails AC-07 on the first real user | Leaving `{ user }` and accepting a guaranteed 401-then-bounce-to-sign-in after every password change — technically safe (never a lockout) but a worse experience than the fix costs to build, which the design note already estimated at "three small edits" |
| D-13 | Built without opening Figma, then corrected against it after the human asked. Compared the built `SetPassword` screen and `PolicyChecklist`/`Toast` components against the actual hi-fi frames (18 nodes, `HF / SCR-010 · Set your password`, all six states at 360/768/1280) and the design system's own component docs. Found and fixed four real defects: (1) `Toast` had a manual dismiss button the component's own Figma description explicitly rules out — *"This is not a screen she has to dismiss: the destination carries it"* — and was missing its check icon; both are now built from the exact asset/copy the design system already defines for this shared component (Figma node 31:11), not invented fresh. (2) The card's heading+intro paragraph and the new-password-field+checklist were flat siblings under `Card`'s uniform 24px gap, which is wrong on both counts — Figma groups each pair at 8px, nested inside the 24px rhythm. (3) The outer column's gap was 24px; Figma's `Auth` wrapper (product name / card / sign-out) uses 32px, matching `SignIn`'s own column. (4) `PolicyChecklist`'s row gap was 8px and its icon 16px; Figma's `Policy checklist` component specifies 4px and 20px | The written SCR-010 spec (`inception/design/screens/SCR-010-set-your-password.md`) carries every state, every copy string and every structural decision in prose, and all of it matched — copy, ordering, field grouping conceptually. But it does not carry pixel-level spacing or the exact shape of a shared component's existing Figma definition, and this codebase's own convention (`app-architecture.md`, `ai/standards/coding-standards.md`'s "every value is a token" rule) is that Figma, not the markdown spec, is the source of truth for measurements. Building only from the prose spec was an assumption that the two never drift, and here they did — a toast with a dismiss button someone would have had to also invent client-side dismissal-persistence logic for is exactly the kind of unrequested scope `ai/quality/review-checklist.md` §7 exists to catch | Treating the written spec as sufficient without the frames — faster, and it shipped a component that contradicted the design system's own documented intent for a component it reused rather than invented |

## Open for the human's confirmation, not blocking D1

| # | Item | Why it is not blocking |
| - | ---- | ----------------------- |
| 1 | V-12's "special character" and length-counting definitions (D-09) | Proceeding under the stated assumption; route a one-line confirmation into V-12's own text via `/ba` |
| 2 | The toast's dismissal — a manual control only, or also a timer | No spec gives a duration; changes nothing structural either way. Route to `/ux` |
| 3 | The V-15 probe produces a **failed** Supabase sign-in event whenever the user picks a good password. If a future lockout-after-N-failures rule is adopted (US-001 open item 3), it must exclude this probe or V-15 needs a different mechanism | Not this story's decision — carried forward to whoever takes the lockout decision |
| 4 | Set-password requests now contribute a second class of request to Supabase's per-IP auth rate-limit budget from this server's one IP (US-001 open item 3, ADR-003) | Gap unchanged, surface wider; a Gate 3 item, not this story's to close |
| 5 | Two consecutive stories (US-002, US-004) have each invented a different way for a route to relate to the auth chain — mounting outside it, and a per-instance gate flag. A third pattern would be worth an ADR titled "how routes relate to the auth chain"; a second is not | The Architect does not expect a third route to need one; flagged so the human can veto |
