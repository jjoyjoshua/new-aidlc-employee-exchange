# US-014 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision | Rationale | Alternatives rejected |
| ---- | -------- | --------- | ---------------------- |
| D-01 | AC-08 stays in scope; this story builds only the **receiving** half (reading its filters from the screen's own query string on mount). No link is built from US-019's blocked-deactivation dialog | US-019/AC-06 already names this story as its supplier by number, in writing, in both directions; dropping AC-08 would need a Gate 1 change-request to remove work this story can do cheaply and correctly; the AC's *Then* is entirely this screen's property and is testable today (design-note §2.1) | Dropping AC-08 from this story's done-list and re-filing it against US-019 — rejected, the receiving half is cheap and the story's own text already justifies the desk filter by naming this exact case |
| D-02 | The desk filter's data comes from a new resource, `GET /api/admin/desks`, served by a new read-only repository/service in `apps/api/src/modules/desks/` — not embedded in the bookings envelope, and not a second desk read inside `modules/bookings` | Per-page bookings responses shouldn't re-send an unchanging desk list on every keystroke; US-016 (next in the epic) needs the same list and would otherwise build a second source for the same fact; ADR-004's own precedent ("put the read where the write will have to live," US-013 §4.1) places it in `modules/desks`, where US-015/US-017 will add the writes (design-note §3.1, §3.2) | Embedding the list in `GET /api/admin/bookings`'s response — rejected, couples two different data lifetimes behind one `Cache-Control` and duplicates a source US-016 will build anyway. A second read inside `modules/bookings`'s existing `AvailabilityRepository` — rejected, that object's every method is `is_active`-filtered or scope-checked by construction, and a sibling method that deliberately omits the filter is a copy-paste hazard on the exact invariant US-006/AC-04 depends on |
| D-03 | The status filter's "Confirmed" and "Completed" values are both computed via a new pure function, `displayStatusPredicate`, added beside (never inside) the existing `bookingDisplayStatus` in `apps/api/src/domain/booking-history.ts` | Both are compound predicates over the two-valued stored enum (`confirmed`/`cancelled`) crossed with `booking_date` vs. `today`; a naive `.eq('status', 'confirmed')` passes a seed with no past-dated row and silently fails on real data — exactly the QA note's stated failure mode. Writing the predicate twice (once as a label rule, once as a filter rule) is the drift ADR-007 exists to prevent (design-note §6) | Inlining the date comparison directly in the repository query — rejected, a second, undocumented implementation of ADR-007's rule in SQL. Editing `bookingDisplayStatus` itself to also return bounds — rejected, `task-surfaces.md` prices an edited rule as Complex and this is genuinely a new, separate concern (the inverse mapping, not the mapping itself) |
| D-04 | Adopting the Architect's recommendation: the date filters use a native `<input type="date">` in a new screen-private `DateField`, not the shared `DatePicker` | `DatePicker` clamps navigation to the 30-day forward booking window and strikes through weekend dates — REQ-006's rules, not this filter's. Reusing it would silently cap AC-01's "reach back over a year" requirement in a component that looks obviously correct because it already exists (design-note §7.4) | Reusing `DatePicker` — rejected outright, the trap the design note names explicitly. **Not yet confirmed with UX** — the native control renders per-locale (`07/09/2026`) rather than the `Mon 7 Sep` format the hi-fi frames draw; carried forward as design-note open item 1 |
| D-05 | Adopting the Architect's recommendation: `Select` and `FilterBar` are screen-private to `screens/all-bookings/`, not added to `components/` | Today there is exactly one consumer, and the components README's own rule keeps a one-consumer component local; the nearest second candidate (US-016's desk inventory) explicitly has no filters (design-note §7.3) | Building them in `components/` now on the strength of SCR-005's handoff calling them "reusable" — rejected as speculative, per the components README's rule that extraction is the second consumer's call. **Not yet confirmed with UX** — carried forward as design-note open item 6 |
| D-06 | Adopting the Architect's interim recommendation: US-013's ST-03 copy ("Nobody has booked a desk yet.") ships unchanged, even though the default view's floor at today means older bookings could technically exist and still trigger it | This story should introduce no behaviour change to US-013's shipped copy; rewording it is a UX/PO call this story doesn't need to make to satisfy its own ACs (design-note §7.1, open item 2) | Rewording ST-03's copy now to hedge the claim — rejected as out of this story's scope. **Not yet confirmed with UX/PO** — carried forward as design-note open item 2 |
| D-07 | `Select` (the Status/Desk filter controls) is a CUSTOM listbox rendered entirely by this page (`role="listbox"`/`role="option"`), not a native `<select>` | Confirmed against the real running app, in both a desktop Windows Chrome and Claude's own browser pane: a native `<select>`'s options POPUP is drawn by the OS/browser chrome, not this stylesheet, and on that platform it renders in a light listbox regardless of `color-scheme` declared on the element — the closed control matched the dark theme, but the open dropdown did not, and no CSS reachable from the page fixed it (tried and reverted: `color-scheme: light dark` directly on the `<select>`, the standard fix for the *usual* cause of this symptom, made no difference here) | Declaring `color-scheme` on the element — tried first since it is the documented fix for this exact symptom in most Chromium versions; rejected once confirmed ineffective in the environment actually used. Leaving the native `<select>` and accepting the light popup as a known platform limitation — rejected once a human reported it as a real defect, not a cosmetic footnote |
| D-08 | `DateField` reverses D-04: it now renders a CUSTOM HTML calendar (`Calendar.tsx`, screen-private), not the native `<input type="date">` popup, on the human's direct request to match the rendered-HTML calendar style used elsewhere in the app (`components/date-picker/DatePicker`'s look). `Calendar` reuses that component's `date-picker.css` chrome but is its own component — `DatePicker` itself is still not reused, for the same reason D-04 gave: it clamps to the 30-day forward booking window and strikes through weekends, neither of which apply to an unbounded admin filter | The human tested the native popup live and asked for the same calendar style already used for booking a desk instead, superseding D-04's native-input trade-off. `min`/`max` (not a fixed booking window) are `Calendar`'s only bounds, and a day outside them renders struck through rather than hidden — the same non-colour cue `DatePicker` uses for its own refused days | Keeping the native `<input type="date">` (D-04) — superseded by direct human request. Reusing `DatePicker` itself rather than building a sibling — rejected, still the exact trap the design note names: it would silently cap this filter at the 30-day booking window and strike through every weekend, which this filter must not do |

| D-09 | `Calendar`'s first and last weeks fill their empty slots with the ADJACENT month's day numbers, dimmed and non-interactive, instead of leaving them blank | The human tested the built calendar live and reported the last row looking "misaligned" — the 28/29/30-only row was in fact correctly column-aligned, but a partial row with nothing after it read as visually cut short. Filling it with muted adjacent-month numbers is the standard calendar convention that avoids that reading, without making those days selectable or navigating on click | Leaving the blank cells as-is (the original, `DatePicker`-matching behaviour) — rejected once a human found it confusing live. Making the adjacent-month numbers clickable (jumping the view and selecting) — rejected as unrequested scope; "dimmed" was the literal ask, not "also navigable" |

| D-10 | Overrode `.date-picker__weekdays`'s gap to match `.date-picker__week`'s, scoped to `.all-bookings-calendar` in this screen's own stylesheet | `components/date-picker/date-picker.css`'s `.date-picker__weekdays` sets no gap between its seven Mo…Su labels while `.date-picker__week` sets `gap: var(--s-4)` between its seven date cells — two flex rows of 7 equal-width items consuming different total gap widths drift apart moving right. A human saw this live (later columns visibly off from their header) | Editing `date-picker.css` itself — rejected: it is a shared, protected-by-convention stylesheet (`DatePicker`'s own props/behaviour are a Complex surface) and this story does not need to touch it. The same latent drift likely affects `DatePicker` on "Choose a booking date" too; flagged as a follow-up, not fixed here |

Cite these as `US-014/D-01` through `US-014/D-10` outside this folder.

Two structural recommendations from the design note are not yet decisions here because they need a human/UX number rather than an engineering call: the exact 360↔768px collapse boundary (open item 5) and the desk `Select`'s brief non-interactive treatment on first load, including its failure copy (open item 4). Both are non-blocking for Gate D1 per `implementation-plan.md`'s Open questions section.
