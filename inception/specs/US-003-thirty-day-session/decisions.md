# US-003 — decisions

> Technical choices made while implementing this story, with the reasoning that produced them. A choice that changes the shape of the system is not recorded here. It goes to the Architect as an `ADR-###`.

| ID   | Decision                                                                                                     | Rationale                                                                                                                                                                                                                                                                                             | Alternatives rejected                                                                                                                                                                                   |
| ---- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-01 | Both new config keys are **optional and defaulted** (`30` / `60`), not newly required                          | Adopted from the design note §3(a): the correct value is the requirement itself, known and identical in every environment. A required key would break every existing `.env` and deployment on the day this merges, purely to make them retype a value nobody needs to choose | A required key, mirroring `OFFICE_TIMEZONE`'s no-default pattern — right for a value that is *wrong* by default (UTC), wrong here, where the default already is the requirement |
| D-02 | Expiry compares against the **throttled** `last_seen_at` directly — no second timestamp, no cache              | Design note §2.2 works the bound: the value understates true last use by at most one throttle interval (0.139% of the 30-day window), and no AC lies within that margin. A second column or an in-process cache buys precision nobody asked for at the cost of new schema or a guarantee that evaporates on restart | A `last_activity_at` column written on every request (rejected by `db-design.md` §1.1 before this story existed); an in-process cache of true last-use times (wrong the moment there are two server instances) |
| D-03 | Step 4 checks expiry **before** deciding whether to stamp, and never stamps an expired session                 | Stamping first would resurrect the session the rule exists to kill, and a single-request test cannot catch the bug — only a two-request sequence can (design note §2.3). This is the one ordering choice in the story with no safe alternative                          | Stamp unconditionally, then check expiry — silently defeats AC-03 for any session that keeps sending requests after it should have expired                                                          |
| D-04 | `stampLastSeen` takes an explicit `at: Date` argument instead of reading `Date.now()` internally                | The value compared (step 4's `nowMs()`) and the value written must come from the same clock reading, or a session could be judged against one instant and stamped with another. A clock inside a repository is also a clock no test can fix (design note §2.4)         | Leave the repository reading its own clock and accept the drift — the existing `attemptSignIn` comment already names exactly this risk for a different clock read in the same file                  |
| D-05 | A failed `markSeen` write is caught, logged at `warn`, and never fails the request it rides on                 | A transient write failure on a renewal must not turn a valid authenticated request into a `500`; the cost of a lost stamp is at most one throttle interval of un-renewed session, retried on the next request (design note §2.5) — the same device `attemptSignIn` uses for a failed revoke | Let the write's rejection propagate and fail the request — turns a session-renewal side effect into an outage for an otherwise-successful action                                                    |
| D-06 | `nowMs: () => number` is the clock seam threaded into `requireSession`, not `infra/clock`'s `Clock` interface   | `composition.ts` already builds exactly one `nowMs` and threads it into the service and router; reusing it keeps one source of "now" in the composition root. `infra/clock`'s `Clock`/`fixedClock` is the nicer interface but introducing it here means two clock idioms wired side by side (design note §2.4) — flagged as a candidate for a later, separate convergence | Migrate `requireSession` (and, to be consistent, the rest of the API) to `infra/clock`'s `Clock` in this same story — widens the diff to a project-wide clock refactor no AC asks for |
| D-07 | `currentUser` is renamed `loadSession` rather than kept and given a second, parallel method                     | It has exactly one caller (`require-session.ts:69`), and it now also reports the session's age, which `currentUser` no longer describes accurately. A rename with one call site costs a compile error if missed, not a silent divergence between two similar methods    | Add a second method (`getLastSeenAt` or similar) alongside the unchanged `currentUser` — two methods doing overlapping reads of the same row is the redundancy `api-standards.md` argues against |
| D-08 | `AuthenticatedUser` (the wire contract) is **not** widened with a `lastSeenAt` field                            | A `libs/contracts` change that ships a server-side timestamp to every browser, for a value the browser never needs to see or act on — the server is the only thing that ever compares against it (design note §2.6)                                                     | Add `lastSeenAt` to the response and let the browser display "signed in since…" — no AC or SCR asks for this, and it would be new UI scope smuggled into a session-mechanics story                |
| D-09 | The boot sequence's browser call goes through the **existing** `GET /api/auth/session` route, not a new one    | The route already does exactly what a cold boot needs — verify the token, load the profile, run step 4 — and its own docblock already names this exact use case (design note §5.1)                                                                                     | A dedicated `GET /api/auth/boot` or similar — a second route doing the same work as the first, for no requirement this story states                                                                |
| D-10 | An `unavailable` result from the boot call leaves the stored session untouched; only an explicit `401` clears it | An outage is not an expiry. Discarding a valid 30-day session because the server was briefly unreachable defeats the entire purpose NFR-009 exists for. The next boot simply retries (design note §5.1, step 5)                                                        | Treat any non-`200` boot response the same way (sign out) — conflates "the server said no" with "the server didn't answer," which are opposite failure modes here                                    |

## Open for the human's confirmation, not blocking D1

| # | Item | Why it is not blocking |
| - | ---- | ----------------------- |
| 1 | The `.max(30)` ceiling on `SESSION_LIFETIME_DAYS` (design note §3(c)) — should an operator be able to lengthen the window past 30 days, or only shorten it during an incident? | Both are defensible; the ceiling is adopted as the default because RISK-010 was accepted against 30 days specifically. Droppable without touching any other decision in this package |
| 2 | Whether the throttle interval (60 minutes) should itself be tunable in production, or is a fixed operational constant like `SIGN_IN_MIN_FAILURE_MS` | Made configurable per the story's own instruction ("Needs session lifetime and sliding renewal to be configuration, not a literal"); flagging because unlike the lifetime, the throttle is a pure cost knob with no AC pinned to its value |

Cite these as `US-003/D-01` outside this folder.
